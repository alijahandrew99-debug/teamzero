## Shipped today

**`keeper/2026-10-12-callback-queue-reentrancy-lock`** — a new sibling of the
stuck-call/duplicate-run family (items 3 and 24), found by looking for
exactly that per this queue's standing brief.

What I found: `placeCallback()` leaves a callback record at `status:
'queued'` for the entire `await voice.placeCall(...)` — the live round trip
to Twilio's API — and only flips it to `'called'`/`'failed'`/etc. after that
resolves. `runCallbackQueue()` runs on a bare 60-second `setInterval` with no
lock around it. If one tick's up-to-20 due calls ever took longer than 60s
in total to place (a slow Twilio response, a burst of due callbacks, a
network stall), the next tick fired anyway, read the same still-`'queued'`
rows, and would place a second real call to the same number before the first
tick's status write had landed. This is the identical shape `startSendJob`'s
own lock (the `activeSends` map) already exists to prevent for the send
queue — this loop just never got the equivalent guard.

I have no evidence this has actually fired in production — it needs Twilio
latency or backlog volume to genuinely exceed 60s — but the window is real
and the failure mode is a customer's own customer getting called twice by
the AI receptionist, which seemed worth closing on sight rather than filing
as "report, don't fix."

Fix: a module-level `callbackQueueRunning` boolean. `runCallbackQueue()`
returns immediately if a previous invocation is still in flight, and clears
the flag in a `finally` so a thrown error can't wedge the queue shut
permanently. Confirmed the `setInterval` is the function's only caller, so
the guard can't block any other legitimate path into it.
