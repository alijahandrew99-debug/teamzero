## Shipped today

**Found a real gap in the call-back retry path that survives item 32's
(10-12) fix.** Item 32 added a re-entrancy guard (`callbackQueueRunning`,
in-memory) so the same process can't re-read a still-`'queued'` callback row
on the next 60s timer tick while the previous tick is still mid-call. That
guard is wiped by any restart, though — and the underlying issue it was
guarding against is still there: `placeCallback()` leaves a callback record
at `status: 'queued'` for the *entire* `await voice.placeCall(...)` (the real
Twilio API round trip), only writing `calledAt`/`status: 'called'` after that
resolves. Kill the process in that window — a deploy, a crash — and the
*restarted* process's queue sweep reads the same still-`'queued'` row and
dials the same customer a second time. Same failure shape as the stuck-call
bug this queue has chased before (items 3/8/32: persisted state doesn't
reflect in-flight work across a restart), just one layer deeper.

Fixed on `keeper/2026-11-14-callback-stuck-calling-sweep`, cut fresh off
current `main`. `placeCallback()` now persists `status: 'calling'` (plus a
`callingAt` timestamp) *before* the await — the queue sweep only ever
re-reads `status === 'queued'`, so a restart mid-call leaves the row
unreachable by the retry path instead of reachable. Deliberately does **not**
auto-requeue a row stuck at `'calling'`, since after a restart there's no way
to know whether Twilio actually placed that call — guessing wrong either
drops a legitimate callback or dials the customer again. Instead a new
10-minute sweep flags anything still `'calling'` after 10 minutes (normal
completion is seconds) as `'failed'`, with a note to check Twilio logs by
hand before any manual retry.

`node --check server.js` clean; all six pre-existing suites pass, 103/103
