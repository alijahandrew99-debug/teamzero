- Picked up queue item 1 (db.js write safety), which the 08-25/08-26 audits
  had left with one open question: does anything actually need the
  "per-file write queue" half, given `db.js` itself is fully synchronous and
  provably race-free on its own? Re-reading `lib/stripe.js` against that
  question turned up a real instance: `creditTopup()` adds top-up
  leads/minutes onto whatever balance the caller last read, and is reachable
  for the same account from two places — the webhook path (synchronous) and
  the `/app` reconcile safety net (`reconcileTopup`, which awaits two Stripe
  API calls before crediting). Two top-ups landing close together, or a
  webhook racing its own safety net, can lose one credit outright: the
  second write overwrites the first before either persists, and a customer
  who paid for a top-up never sees the balance move. Same shape as the
  item-14 metering bug from 09-02 (stale snapshot across an `await`), just
  on additive balance fields instead of a usage counter, and never
  previously audited because it doesn't match either prior audit's search
  pattern (metering / billing-flag code, not top-up-credit code).
- Shipped `keeper/2026-09-13-topup-write-race`: added `db.withLock(key, fn)`,
  a small per-key async promise queue (generic, so any future async-gap race
  has somewhere to plug in), and routed `creditTopup` through
  `db.withLock('account:'+id, ...)`, re-reading the account fresh once the
  lock is held instead of trusting the possibly-stale object captured before
  the caller's own awaits. Verified the primitive actually serializes with a
  standalone repro (three concurrent read-await-write jobs against a shared
  counter — without the lock they race to 1, with it they correctly reach
  3, confirmed both ways). `node --check` clean on both touched files; all
  four suites still pass (87/87), unaffected since this only changes
  `creditTopup`'s internal execution order, not its external behavior for a
  single caller.
  Deliberately scoped narrow: left `reconcileCheckout`'s own staleness check
  alone (it's a non-additive idempotency flag, so a redundant duplicate
  write there is mostly harmless — lower stakes than a lost credit) and did
  not touch the rest of `stripe.js`'s webhook-event branching. There's no
  Stripe test harness in this environment, and live billing webhook logic
  is not the place to widen a fix beyond the one concrete bug found.
