## Shipped today

**`keeper/2026-10-13-voice-call-map-leak`** — a new sibling of the stuck-call
family (queue item 3), found by looking for exactly that per this queue's
standing brief, in a place the original 2026-08-26 audit didn't check.

What I found: that audit explicitly swept every in-memory tracker it could
find (`jobs`, `sendJobs`, `callJobs`, `phoneJobs`, `activeSends` in
`server.js`) and concluded none could go stuck without a persisted row. It
never looked at `lib/voice.js`'s own `calls` Map — the live conversation-turn
state for an in-progress call, keyed by Twilio call SID. `startCall()`'s only
cleanup ran `if (calls.size > 500) for (...) delete entries older than 1h`,
gated on the map first passing 500 *concurrent* entries. At this product's
call volume that gate essentially never opens, so a call whose status
callback never arrives — a lost Twilio webhook, or a bug throwing before
`endCall()` runs — leaks its entry there permanently: a slow, unbounded
memory leak for as long as the process stays up between deploys.

Fix: replaced the size-gated inline check with an unconditional 15-minute
`setInterval` that sweeps anything older than 1 hour, independent of call
volume — same staleness bar the old check used. Calls that complete
normally are unaffected (`endCall()` still removes them immediately on the
happy path).

Verified: `node --check lib/voice.js` clean; `test-voicebilling.js` (7/7)
and `test-reps.js` (37/37) both still pass — neither exercises this Map
directly, which confirms no regression in the call-state paths that do.
Cut fresh off current `main` (`0ecb712`), a direct-ancestor fast-forward
merge, conflict-free by construction.

Also re-checked queue item 1 (db.js write safety) before picking today's
item, since it's the oldest open line. Independently reached the same
conclusion the 08-25/10-12 shifts already recorded: every write in
