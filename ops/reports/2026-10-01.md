**New critical-tier finding (not mine — an independent code-audit process,
verified by this shift today):** `lib/db.js`'s `read()` treats "this file
exists but won't parse" identically to "there are no records yet." A store
file that goes zero-length or truncated — an unclean process kill (`write()`
renames without `fsync`, so ext4 can publish an empty file on an OOM kill),
or a full disk — gets silently treated as empty, and the *next ordinary
write* (one signup, one live call) persists that emptiness over the real
file, permanently. There are no backups anywhere in this repo. Reproduced
end-to-end against the real `db.js`: 3 accounts + 2 calls seeded, file
zeroed, one write later both files hold exactly one new row and the rest is
gone for good. The fix (already written, tested, pushed — not merged) only
touches `read()`: an unparseable file is renamed aside to
`<file>.corrupt-<timestamp>` and logged loudly instead of being discarded; a
failure to *read* the file (cold start, `EMFILE`/`EIO`/`EACCES`) is left
strictly alone so a transient blip can't itself destroy a healthy store.
Added to the queue as item 28.

Re-verified in an isolated worktree, one real `git merge --no-ff` at a time
