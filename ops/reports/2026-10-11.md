## Shipped today

**`keeper/2026-10-11-fallback-spam-billing`** — item 11 ("`/voice/status`
fallback billing") was marked closed on 10-08, but only half of it actually
landed.

What I found: the 10-08 merge (`8616294`) fixed the fallback path's
*idempotency* — a duplicate Twilio status callback can no longer double-bill
the same call. It never ported the **other** half of what item 11 was
originally about: the live path excludes robocalls, screened-out callers, and
dead air from billing (`callerSpoke && !call.spamCall`); the fallback — taken
whenever a deploy wipes the in-memory call before the final status webhook
lands, which is routine since `main` auto-deploys — still billed
`CallDuration` unconditionally, with no idea the call had ever been flagged.
`call.spamCall` is purely an in-memory flag and never reaches the db row, so
the fallback had nothing to check even if it had tried.

This surfaced from the 2026-10-07 `keeper-audit` report, which I read in full
for the first time this shift — the last two shifts (10-09, 10-10) checked
only the git branch it named, found that ref was a stale pointer at the
already-merged `8616294`, and moved on. The report's own text underneath that
pointer correctly flagged a second, un-superseded bug and named
`audit/2026-08-26-voice-status-fallback-billing` as the branch that (partially)
addresses it. I confirmed the gap directly against live `main:server.js`
rather than trusting either the queue's "closed" note or that branch — it's
real, and it's been live since the 10-08 merge.

Fix: the fallback now derives the same exclusion from what IS persisted —
`prior.outcome === 'spam' || 'screened-out'` (every `call.spamCall = true`
site sets one of those two, checked all three) and `prior.transcript` (saved
every turn) to recompute `callerSpoke` the same way the live path does.

Verified: added a new case to `test-voicebilling.js` reproducing the exact
shape (robocall phrase tripwire → simulated deploy wipe → the orphaned call's
final webhook) — confirmed it **fails** against the pre-fix code (stashed the
fix, re-ran, restored it) before trusting it as a real regression test.
`node --check` clean on both files; all six suites pass, **104/104** (up from
103 — the new case). Confirmed the branch merges clean against current `main`
(a direct-ancestor fast-forward, conflict-free by construction) and
individually against the three other open branches touching nearby
`server.js`/billing lines (`keeper/2026-10-09-transfer-leg-cost-rebase`,
`keeper/2026-10-10-mutate-account-autofill`, `audit/2026-09-02-consume-stale-snapshot`).
