## Finding 1 — Unauthenticated POSTs to `/voice/*` each force a full database write

**New. Severity: high, growing with customer count. Confidence: high on the mechanism.
Fixed — `audit/2026-09-09-voice-webhook-log-flood`.**

`server.js:1143`. A webhook that fails signature verification is logged *before* the caller
is authenticated:

```js
if (!voice.verifySignature(base + p, params, sig)) {
  db.logActivity('system', { agent: 'VOICE', msg: 'Rejected unsigned webhook on ' + p });
  res.writeHead(403, ...); return res.end('bad signature');
}
```

`db.logActivity` (`lib/db.js:563`) reads the whole activity file, unshifts, runs
`capPerAccount` over every row, re-serialises and writes it back. Its designed steady state
is 500 rows **per account**, so the cost grows with the customer count — and every anonymous
request pays it in full. There is no rate limit on `/voice/*` (they exist on `/login`,
`/signup`, `/forgot`, `/api`, the callback form and the assistant; `/voice/*` is not among
them).

Measured against a `DATA_DIR` filled to the size `capPerAccount` itself permits. Node is
single-threaded, so this time is the event loop **fully blocked**, not one slow request:

| customers | activity.json | per rejected POST | req/s to saturate |
|---|---|---|---|
| 10 | 0.8 MB | ~10 ms | ~100 |
| 50 | 4.0 MB | ~36-56 ms | ~20-28 |
| 200 | 15.9 MB | ~170-230 ms | ~4-6 |

(Run-to-run variance was ±30%, so treat these as orders of magnitude, not precise figures.)

When the loop saturates, live `/voice/turn` webhooks queue behind it, Twilio gives up at 15s,
and the caller hears Twilio's own "application error" recording. The product's core function
fails — from one host, with no credentials, against a public endpoint.

**Being straight about today's blast radius:** at a handful of customers this is a ~10-20x
amplifier, not a one-host kill; you would need a genuine flood. It becomes trivially fatal
somewhere around 50 customers, which is inside the growth this business is planning for. Fix
it while it is cheap.

**It also survives the pending backlog.** `keeper/2026-09-02-db-write-compact` drops the
`null, 2` pretty-printing, which is the obvious mitigation. I measured it: 230 ms → 158 ms at
200 customers, 36 ms → 34 ms at 50. A 20-30% improvement that does not change the conclusion.

The sibling handler `/sms/incoming` (`server.js:1053`) already returns 403 **without**
writing, so this is an inconsistency rather than a deliberate design.

**Fix:** the log line is gated to once a minute, globally. A genuinely misconfigured Twilio
console fails *continuously*, so one line a minute still surfaces it. The gate is global
rather than per-IP because the goal is capping total write rate, and an attacker picks their
own source addresses. `node --check` clean; server boots.

## Finding 2 — Spam strikes stop counting forever once a number's record decays

**New. Severity: medium. Confidence: certain — reproduced against the real module. Fixed —
`audit/2026-09-09-spam-strike-decay`.**

This one corrects last week's report, which listed under *"What I checked and found sound"*:

> *`spam.strike` is safe (`lib/spam.js:94-106`) — `rec()` through `patchCollection` with no
> `await` anywhere, so the read-modify-write is atomic.*

That is true, and it is not the bug. The read-modify-write **is** atomic. The logic inside it
is wrong.

`lib/spam.js:94-100`. `strike()` asks `rec()` whether a record exists — but `rec()` returns
`null` for a record past the 30-day decay window (`lib/spam.js:80`). So the first strike after
a decay takes the **insert** branch and writes a *second* row under the same `id`. From then
on `rec()`'s `.find()` hits the stale row first, decides it is stale, and returns `null` —
permanently. `db.pushCollection`/`patchCollection` (`lib/db.js:481-494`) enforce no key
uniqueness, so nothing catches it.

Reproduced against the real `lib/spam.js`:

```
after 1st strike, strikes() = 1
aged record past decay. strikes() = 0        (correct: clean slate)
  strike #1 returned total=2; strikes() now reads 0
  strike #2 returned total=2; strikes() now reads 0
  strike #3 returned total=2; strikes() now reads 0
rows in spamwatch.json: 4 | distinct ids: 1
blocked? false
```

Concrete failure: a number takes one dead-air strike, goes quiet for 31 days, then starts
robocalling again. It can never reach `BLOCK_AT` (3), so it is never auto-blocked, layer 1
(`<Reject>` on `/voice/incoming` — the free layer) never engages, and every future robocall
from it is answered and costs AI + TTS + recognition. That is exactly the repeat-offender
population the module exists to catch; a one-off robocaller was never the problem.
`spamwatch.json` also gains a duplicate row per strike, forever, and nothing prunes it.

**Fix:** patch-vs-insert is now decided by whether a row physically exists, which is a
different question from whether its points still count. Decay semantics unchanged — a decayed
record is still a clean slate. Regression test added to `test-spam.js`; it fails on the
unfixed file (3 failures) and passes on the fix. Suite: 22 passed, 0 failed.

## Already known — cross-references, not new findings

I found these independently before reading the prior reports. Recording them only to confirm
a second pass reaches the same conclusions, with one refinement.

**Global retention caps on `calls` and `smsThreads`** (`lib/db.js:188`, `:361`) — 2026-08-26
finding 3a, 2026-09-02 finding 2, fixed on `keeper/2026-09-05-per-account-retention`. Last
week's treatment is better than mine: it catches that `capPerAccount` walks *forward*
assuming newest-first, while `calls`/`smsThreads` `push` oldest-first, so a naive reuse would
keep the **oldest** rows and delete everything recent. Anyone reviewing that branch should
check the ordering and that a test asserts which rows survive.

*One refinement.* Last week judged that "at today's customer count neither cap is being hit."
The arithmetic is nearer than that implies: COST.md puts a Front Desk customer at 150-250
answered calls per 500 minutes, so ~300-500 calls/month each at the 1,000-minute allowance.
**3,000 rows is roughly 6-10 full-allowance customers' worth of a single month.** Whether
that threshold is actually being crossed depends on real per-customer usage, which is
COST.md's own open question #4 and which neither of us can see from here. So: the trigger
point is single-digit customers, not hundreds — worth knowing when scheduling the merge.

Downstream consequences I traced, in case they help prioritise: `stats.callerHistory`
(`lib/stats.js:120`) reads `db.getCalls(accountId, 3000)`, so evicted history means returning
callers stop being recognised (`server.js:1260`) **and** an established customer stops
counting as `known` at `server.js:1222` — becoming eligible for spam screening, and, if they
go quiet for two gathers (`server.js:1431`), hung up on and struck as spam.

**`/voice/status` restart-path billing** (`server.js:1845-1853`) — covered by
`audit/2026-08-26-voice-status-fallback-billing` (missing spam/dead-air exclusions) and
`keeper/2026-09-03-billing-idempotency` (no billed stamp, so a redelivered callback re-bills).
I confirmed both branches contain what they claim and that **they merge cleanly together**.

## Correcting an over-claim of my own

Before reading last week's report I had written up the shared `.tmp` filename in `db.write()`
(`lib/db.js:45`) as a live two-process corruption window, reasoning from `render.yaml`'s
`healthCheckPath` comment that Render runs old and new instances concurrently during a deploy.

Last week was more careful and knew something I did not: **Render generally does not do
zero-downtime deploys for disk-backed services**, and this service is disk-backed. So the
overlap window probably does not exist, and last week correctly filed it as unsettled pending
a look at the Render dashboard rather than as a finding. I defer to that. `keeper/2026-09-04-unique-tmp-write`
fixes it anyway for one line, which is worth taking regardless of the answer — but it is
insurance, not an active bug, and I was wrong to write it up as one.

The related amplification is real and worth stating once: `read()` (`lib/db.js:43`) swallows
a parse error and returns the fallback, so *if* a file ever did become unparseable, every
reader sees an empty dataset and the next append (`createAccount`, `logActivity`, `saveCall`,
`addLeads`, `addToQueue`, `addAppointment`, `pushCollection`) writes that empty view back —
turning transient corruption into permanent total loss. `updateAccount` is safe by accident
(no match → returns before writing); it is the exception, not the rule.
