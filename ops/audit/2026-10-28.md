## Finding 1 — "let Dawnpipe send for you" can never send

**`server.js:3537-3538`** (the gate) · **`server.js:15-22`** (the resolver it
should have used) · severity **High** · confidence **high, reproduced end to end
against the real server**

### The two halves that disagree

One-click sending stores a *marker*, not credentials. `server.js:3436`:

```js
db.updateAccount(acc, { smtp: { useDawnpipe: true, fromName, fromEmail: sys.fromEmail || sys.user, user: sys.fromEmail || sys.user } });
```

No `pass`, deliberately — that is the entire point of the feature, and
`test-sending-mode.js` already asserts it ("useDawnpipe marker, no password
stored"). Everything that sends therefore resolves the config through
`outboundSmtpCfg()` (`server.js:15-22`), which swaps in the system mailbox:

```js
function outboundSmtpCfg(account) {
  const s = (account && account.smtp) || {};
  if (s.useDawnpipe && mailer.enabled()) {
    const sys = mailer.systemCfg();
    return { ...sys, fromName: s.fromName || sys.fromName };
  }
  return s;
}
```

`startSendJob` does exactly that (`:499`), and its own credential gate at `:527`
reads the resolved config, so the job is correct. The fail-fast gate in front of
it is not — `server.js:3537`:

```js
const cfg0 = account.smtp || {};
if (!cfg0.user || !cfg0.pass) return json(res, { error: 'Connect your sending mailbox first (Your Business tab → SENDING).' }, 400);
```

`cfg0.pass` is `undefined` for every Dawnpipe-mode account, so the gate refuses
the request the job behind it would have completed. Its own comment says it is
there so "an async job's error is easy to miss" — it now manufactures the error
it was added to surface.

### Why the UI walks straight into it

`/api/state` (`server.js:2492-2499`) reports Dawnpipe mode as
`{ mode: 'dawnpipe', connected: true }`, and the browser's own gate
(`views/app.html:2341`) is `STATE.smtp.connected`. So the button is enabled, and
the one-button send runs its two calls in order (`views/app.html:2357-2358`):

```js
await api('/api/queue/approve-all',{profileId:pid()});
const r=await api('/api/send/run',{profileId:pid()});
```

The approve-all **succeeds**. Every pending draft is flipped to `approved`. Then
the send 400s with a toast telling the customer to connect the mailbox they
connected thirty seconds ago, on a tab that is still showing it as connected.
There is no path out of this inside the product except connecting a personal
Gmail — i.e. abandoning the feature.

### Reproduction

Against the real server, through HTTP, as a logged-in Front Desk account
(added to `test-sending-mode.js`; the first two assertions fail on `main`):

```
== Dawnpipe mode can actually SEND ==
  PASS  back in dawnpipe mode
  FAIL  send accepted in dawnpipe mode -> {"status":400,"json":{"error":"Connect your sending mailbox first (Your Business tab → SENDING)."}}
  FAIL  not refused as an unconnected mailbox -> {"error":"Connect your sending mailbox first (Your Business tab → SENDING)."}
```

### How live this is, honestly

It fires exactly when `SYSTEM_SMTP_USER`/`SYSTEM_SMTP_PASS` are set, because
that same condition (`mailer.enabled()`) is what reveals the button —
`views/app.html:2158-2162` hides the whole block otherwise. So:

- **System mailbox configured** → the button is on screen, anyone who clicks it
  loses the ability to send, permanently and silently. Live bug.
- **System mailbox not configured** → the button is hidden, nobody can enter
  Dawnpipe mode, and this is latent until the day it is switched on.

`render.yaml` carries no `SYSTEM_SMTP_*` entries, but it also does not carry
several variables the product plainly uses, and AUDIT.md records password reset
as verified end to end — which needs that mailbox. **`GET /health` returns
`mail: <bool>` and answers this in one anonymous request; this environment's
network policy blocks dawnpipe.com, so I could not.** Worth a glance before
deciding how fast to merge.

### The fix — pushed on `audit/2026-10-28-dawnpipe-send-gate`

One line: the gate reads `outboundSmtpCfg(account)`, the same resolved config as
the job it guards, so the two can no longer disagree. An account with no mailbox
at all is still refused with the same message. `test-sending-mode.js` covers
both directions. 13 passed, 0 failed; other five suites unchanged
(17/7/37/18/15); conflict-free against `main` and against the other branch
pushed today.

**Related, and NOT fixed here:** `keeper/2026-09-16-dawnpipe-send-warmup` (6
weeks open) is the other half of this feature — in Dawnpipe mode the warmup
state still belongs to the customer's *own* domain or is absent entirely, and
`warmupAllowance()` reads absent as unlimited. That branch touches this exact
code path and did not catch the gate, which is a reasonable argument for merging
the two together and re-reading the whole mode once.

## Finding 2 — one rented phone line, counted twice

**`server.js:2814-2815`** · severity **Medium** · confidence **high,
reproduced**

```js
const linesHeld = ((account.voice || {}).numberSid ? 1 : 0)
  + db.getProfiles(acc).filter((pr) => pr.voice && pr.voice.numberSid).length;
if (!stripe.isOwner(account) && linesHeld >= 2) { /* refuse */ }
```

For an account set up before per-business numbers, those two terms can be the
**same purchase**. `db.profileVoice` (`lib/db.js:244`) serves the legacy
account-level config for the profile it was bound to, and `db.saveProfileVoice`
(`lib/db.js:258`) deliberately seeds from that resolver — so the first
per-profile save copies the number *and its `numberSid`* onto the profile while
the original stays in the account slot. That seeding is correct and load-bearing
(its comment explains that writing a partial patch cold would shadow the legacy
number and kill the line). The counter underneath it just reads the result as
two lines.

Triggering it takes one ordinary action: any save on the AI Answering tab, the
call-back toggle (`server.js:3171`), a release, or a reassign. After that the cap
is spent, and "add a line for my second business" returns *"Your account already
rents 2 phone lines. Email support@dawnpipe.com"* for a single DID that Twilio
bills us $1.15/month for, once.

### Reproduction

Real `lib/db`, throwaway data dir:

```
numbers actually rented on Twilio: 1 (PN_one_real_line)
linesHeld before any voice save   : 1
account.voice.numberSid           : PN_one_real_line
profile1.voice.numberSid          : PN_one_real_line
linesHeld after one greeting save : 2
buy a number for Bob Electrical   : REJECTED 400 — "Your account already rents 2 phone lines."
```

### The fix — pushed on `audit/2026-10-28-count-phone-lines-once`

Count distinct `numberSid`s, so the cap measures purchases — which is what it
was protecting. `test-voiceprofiles.js` now drives it through HTTP on the legacy
account: it saves a greeting, its second business buys a line (the purchase is
stubbed, so the test never reaches Twilio), and a third buy is still refused.
20 passed, 0 failed; other five suites unchanged.

I cannot see `data/` from here, so I do not know how many accounts still hold an
account-level `voice.numberSid`. The per-business change (`f3832bb`) is recent
enough that "the owner's own account and the earliest customers" is the likely
answer.

## Finding 3 — `/api/scout/brief` has no meter, no cap and no rate limit

**`server.js:3631-3634`** → **`lib/agents.js:552-563`** · severity **Medium** ·
confidence **high on the code, unmeasured in production** · reported, not fixed

```js
if (p === '/api/scout/brief' && req.method === 'POST') {
  const f = parseJSON(await readBody(req));
  return json(res, await agents.scoutBrief(acc, f.profileId));
}
```

Every other endpoint that spends AI money has one of three guards, and most have
two:

| Endpoint | Guard |
|---|---|
| `/api/prospect/run` | lead quota + clamp + per-account job |
| `/api/outbound/run`, `/api/keeper/run` | metered per lead, re-read each iteration |
| `/api/leads/import` | clamped to `usage.remaining` |
| `/api/queue/adjust` | 20/hour, and its comment says why |
| `/api/assistant` | 40 per 6 hours |
| `/api/voice/findphones`, `/api/voice/callrun` | `canSpend` + one job per account |
| **`/api/scout/brief`** | **none of the above** |

`scoutBrief` is a Sonnet call with web search enabled and `maxTokens: 6000`
(`lib/agents.js:560`) — the "market brief" COST.md prices as one of the three
lead-gen calls that cost real money per run. There is no rate limit, no job lock
and no quota consumption, so a single account can hold many in flight at once.
The trigger does not need a hostile stranger: a 7-day trial takes a card and
charges nothing until day 8, and `stripe.hasAccess` is true throughout, so the
cost lands on the owner's Anthropic key against revenue that may never arrive.
AUDIT.md #2 calls precisely this shape critical.

`/api/profile/autofill` (`server.js:2526-2531`) is the same shape one notch
down: the 2-free-autofill counter bounds a *locked* account, and a paid account
is unbounded — each call fetches up to seven pages of a customer-supplied URL
and then calls the model. (It is also the SSRF surface already queued from
09-16.)

**Not fixed because the number is a product decision, not a bug fix.** The
house idiom would be one line beside the handler:

```js
if (rateLimited(req, 'brief', 6, 60 * 60 * 1000)) return json(res, { error: '…' }, 429);
```

Six an hour would never touch a customer using a *weekly* brief the way it is
sold, but picking the ceiling — and deciding whether a brief should also draw
down the lead allowance, which is a pricing question — is Alijah's call, not
mine.

## Checked and sound

Gone through under this lens and found correct, so a future run need not
re-derive them:

- **`/webhook/stripe` → `stripe.applyEvent`** (`lib/stripe.js:488-592`). I went
  after the duplicate-commission case specifically, because Stripe sends BOTH
  `invoice.paid` and `invoice.payment_succeeded` for one invoice and both are
  handled. `reps.recordCollection` dedupes on `('recurring', invoiceId)`
  (`lib/reps.js:216-219`), and — the part that matters — the whole read-check-write
  is synchronous `fs`, with no `await` between the `alreadyPosted` read and the
  `pushCollection` write, so two simultaneous deliveries cannot interleave on one
  process. Same conclusion for `creditTopup`: its `topupSessions` check is
  sync, and `reconcileTopup` re-reads the account *after* its `await fetch`
  rather than before. **This safety is single-instance only** — it is another
  reason not to scale Render past one web instance while the store is flat JSON.
- **`stripe.reconcileCheckout`** (`lib/stripe.js:124-180`). Ownership is required,
  not merely checked when present (`client_reference_id !== account.id` →
  false); a session id is not a bearer token for entitlement because the live
  subscription is re-read and must be active/trialing; replay is stamped in
  `reconciledSession`. The comments explain each of those, and the code matches
  them.
- **Tenant scoping across every handler that takes an id from the request.**
  `updateProfile`, `deleteProfile`, `updateLead`, `updateQueueItem`,
  `updateAppointment`, `updateCallback`, `getCallbacks`, `getThread`/`saveThread`
  all match on `accountId` AND `id`. `db.patchCollection` is the one unscoped
  writer, and its three callers (`reps`, `commissions`, `spamwatch`) are either
  owner-only or keyed `accountId|phoneKey`.
- **`db.updateCallback`'s write-once consent lock** (`lib/db.js:534-551`). The
  TCPA evidence fields cannot be overwritten once `consentAt` is set, and `at`
  / `id` / `accountId` are stripped from every patch. The SMS "YES" path
  (`server.js:1150-1158`) relies on exactly that.
- **`/f/<slug>` call-back form** (`server.js:962-1015`). Slug slice is right,
  honeypot before validation, phone normalised to E.164 before anything is
  stored, consent must be an affirmative `'1'`, the IP and UA are recorded, and
  the dial is deferred with `setTimeout` so the page never waits on Twilio.
- **`/partners/apply`** (`server.js:2158-2175`). Rate-limited 5/hour, every
  field length-capped, email shape checked, and the mailer call is
  fire-and-forget with a `.catch` and a failure logged to the activity feed.
- **`hooks.emit`** (`lib/hooks.js:33-55`). Returns nothing, throws nothing, and
  every `fetch` carries both `.then` and `.catch` — so the `/sms/incoming`
  booking path calling it without a `.catch` cannot produce an unhandled
  rejection. (`process.on('unhandledRejection')` at `server.js:50` is a second
  net.)
- **The night-shift scheduler** (`server.js:709-753`). `lastRunDate` is stamped
  before the gates so a skip cannot loop; `hasAccess` and then `usage.remaining`
  are both checked, and the `continue` on an exhausted allowance happens *before*
  `keeperRun`, so a phone-only tier (`receptionist`, `leads: 0`) cannot start
  unmetered drafting from a schedule it is allowed to save.
- **The AI Receptionist tier against the paywall.** `leads: 0` is honoured
  everywhere it needs to be: `/api/prospect/run` 402s, `/api/leads/import`
  clamps to 0, `outboundRun` and `keeperRun` break on `remaining <= 0` per
  iteration. The only wart is cosmetic — a receptionist who clicks Find leads is
  told *"You've used all 0 leads this month. It resets next month"* instead of
  being offered the upgrade that is the whole point of the tier.
- **`/api/admin/reps/pay`** (`server.js:3288-3306`). `payoutBlocked(null)`
  returns a reason rather than throwing, so a bad `repId` is a 400 and not a
  500; `held` and already-`paid` rows are skipped; the batch id lands on every
  row it touched.
- **`/api/voice/numbers/release` and `/reassign`**. Both clear the number from
  wherever it actually lives, including the legacy account slot, and reassign
  refuses to guess when more than one business holds a line.

## Next run

**Lens (c), security.** Six weeks since 10-14, and it is the lens with the worst
tail risk on a product holding customer PII, Stripe ids and mailbox
credentials. Two concrete starting points noticed this week but properly lens
(c):

- **`SESSION_SECRET` unset is still only a default string.** `suppress.tokenFor`
  / `parseToken` (`lib/suppression.js:31-44`) fall back to
  `'dev-insecure-secret'`, and `/u/<token>`'s page interpolates `parsed.email`
  into HTML **unescaped** (`server.js:2086`). With the real secret that is
  unreachable; with the default it is a forgeable reflected XSS *and* a way to
  unsubscribe anyone on any account. The "fail loudly when `SESSION_SECRET` is
  unset" queue item from 09-16 is the fix, and this is the second reason for it.
- **`views/app.html`'s inline `onclick` handlers pass data through `esc()` into
  a JS string inside an HTML attribute** (e.g. `removeSuppression('…')` at
  `:1708`). The browser HTML-decodes the attribute before parsing the JS, so
  `&#39;` becomes a real quote — the 09-16 `esc()` fix does not cover this
  context. Today the only data that reaches it is the account's own, which makes
  it self-XSS, but the `data-*` + delegated-listener item already in the queue
  is the real answer.

Then **(a)** again or **(d)**. **Lens (b) should keep sitting out** — four of
ten runs have taken it and the answer every time was "move off flat JSON", which
is a project, not a finding. Note, though, that finding (b)-adjacent reasoning
turned up in *this* run's **Checked and sound**: the webhook dedupes are correct
only on one instance, so if Render is ever scaled, (b) stops being a project and
