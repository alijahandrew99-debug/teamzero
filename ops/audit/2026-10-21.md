## 1. A call a human took over gets a booking the human never made — FIXED

**`server.js:1878-1881`, `server.js:2025-2062`** · confidence: **high** ·
reproduced end to end · branch pushed

`/voice/status` runs the hangup salvage on any call that ends without
`call.saved`: it reads the transcript with the model, writes an appointment, and
texts the caller a confirmation (`:2061` → `notify.announceBooking` →
`lib/notify.js:101` → `sendSMS`). That is exactly right for the case it was
written for — somebody who gave up mid-sentence, whose name and "tomorrow
morning" would otherwise die with the call.

Three endings never set `saved`, so the salvage ran on them too. The worst is
the transfer:

```js
// server.js:1878
if (st === 'completed' || st === 'answered') {
  if (call) db.saveCall(call.accountId, { sid, outcome: 'transferred', transcript: call.turns });
  res.writeHead(204); return res.end();
}
```

`DialCallStatus: completed` means a person picked up and the two of them
finished the call. Whatever they agreed happened off our transcript. The salvage
then reads the only half we have — the part *before* the transfer — and treats
it as an unanswered request.

**The failure, driven as signed Twilio webhooks against the running server:**

1. Caller: *"my boiler is not firing, can someone come tomorrow morning"*
2. The agent transfers; the owner picks up; they sort it out between them.
3. `/voice/dialback` marks the call `transferred`. Correct so far.
4. `/voice/status` arrives. Salvage runs, reads step 1, and writes an
   appointment — `whenText: "tomorrow morning"`, `source: "inbound call (caller
   hung up)"`. The outcome flips from `transferred` to `callback`.
5. The caller receives: **`Ace Plumbing: you're booked for tomorrow morning. Re:
   boiler not firing. Need to change it? Call +1555…`**

Nobody booked that. If the human agreed a different time, the caller now holds a
text contradicting them. If the human booked it properly in their own diary, the
owner has it twice. If the human talked them out of a visit, the owner has a job
on the calendar that does not exist. The caller is the one person in this who
has no way to tell which is true.

Transfers are a headline feature — *"this is the moment I'd patch you straight
through"* — and any caller who states a need before being put through triggers
it. This is not an edge case; it is the normal shape of a transferred call.

The same gate leaks at two other endings:

- **`server.js:1649` — the caller opted out.** The `dnc` branch suppresses the
  number, logs it, hangs up. Salvage then builds a callback out of whatever they
  said *before* the opt-out and texts the number that, seconds earlier, told us
  to stop. Reproduced: an SMS addressed to a number already on the suppression
  list, sent by us, after we recorded the opt-out.
- **`server.js:1529` and `:1643` — a robocall.** Both spam paths hang up and
  deliberately bill nothing, then pay for a 400-token extraction over the
  recording's pitch anyway, with the same appointment-and-text path open at the
  end of it.

**Fix:** set `call.saved` at all three endings. It is the flag the salvage gate
already reads and already documents as *"hangup salvage must not create a
duplicate"*; `saved` now means **handled** — booked, callback written,
transferred to a person, or deliberately ended.

`test-voicesalvage.js` drives all four cases, with the model stubbed to the most
generous possible read (`wantsCallback: true`, a name, a time) so a clean result
proves the gate and not a shy model, and the Twilio REST API intercepted at the
fetch layer so no text can leave a test run. **Fails 9 of 15 on the current
`main`; passes 15/15 on the branch.** The fourth case asserts the salvage still
rescues the caller it exists for.

## 2. A slow mail server makes a live caller hear "an application error" — FIXED

**`server.js:1845`** · confidence: **high** · measured · branch pushed

`/voice/msg` is the graceful failure: the plan's minutes are gone, so instead of
hanging up on the customer's customer we answer, take a message, and tell the
owner to top up. It was the one voice webhook that awaited an email.

```js
// server.js:1845
await notify.callSummary({ ... });
```

That puts `lib/smtp.js` on the critical path of a live call. smtp.js allows
**20s to connect and 30s idle** (`lib/smtp.js:131`) — deliberately, because mail
servers stall. Twilio abandons a webhook at **15s** and speaks *"an application
error has occurred"* to the caller.

**Measured** against a mail server that accepts the socket and never speaks:
`/voice/msg` answered in **20,042ms**. Fire-and-forget: **37ms**.

So the path whose entire job is to fail gracefully is the one that fails loudly,
and it does so precisely when the owner is already losing jobs to an exhausted
allowance. Nothing is lost by answering first — the message is written to the
diary several lines above the await, so the await only ever delayed the "got it,
someone will call you right back" the caller is waiting on. Every other notify
call on a voice webhook already runs fire-and-forget; `/voice/status:2016` says
why in as many words.

`test-voicemsg.js`: 5 assertions, the latency one fails on `main` at 20s.

## 3. The restart/retry billing path still ignores every billing exclusion — NOT FIXED (a branch already exists)

**`server.js:1911-1934`** · confidence: **high** · reproduced · **already fixed
on two unmerged branches**

Carried from 2026-08-26 and 2026-10-07. Re-verified this run rather than taken
on trust, because the fallback is the branch a Render deploy lands in.

The live path at `:1947` is careful:

```js
const minsToBill = (callerSpoke && !call.spamCall) ? Math.ceil(dur / 60) : 0;
```

The fallback at `:1920-1930`, taken whenever the in-memory call is gone, is not:

```js
const mins = Math.ceil(dur0 / 60);
const already = Number(prior.billedMin || 0);
...
if (mins > already) plans.consumeVoiceMinutes(owner2, mins - already, stripe.isOwner(owner2));
```

It knows what the SID was already charged, so an identical retry of a *normal*
call is free — that part works, and `test-voicebilling.js` proves it. But it
never asks whether this call was billable at all. A call the live path correctly
charged **zero** minutes — a robocall, or dead air where nobody spoke — has
`billedMin: 0` on disk, which the fallback reads as "not yet charged" and bills
in full.

**Reproduced:** a 95-second robocall, hung up on by the tripwire, outcome
`spam`, `billedMin: 0`, zero minutes billed. One status retry later: **2 minutes
charged to a paying customer's allowance.**

Triggers whenever the in-memory call is gone before the callback lands: a deploy
mid-call (this repo auto-deploys `main`), or any Twilio redelivery after the
first ack is lost.

I did not fix it. `audit/2026-08-26-voice-status-fallback-billing` and
`keeper/2026-10-11-fallback-spam-billing` both already do, and a third fix on the
same twenty lines helps nobody. **Merge one of them.**

## 4. A speculative think that errors hangs up the call — NOT FIXED (needs a judgement call)

**`server.js:1444-1450` vs `server.js:1619-1629`** · confidence: **medium-high**
(code path certain; frequency depends on API error rates)

The speculation machinery launches a think off the partial transcript and reuses
it only if the final transcript matches. The race path protects that bonus
attempt explicitly:

```js
// server.js:1619 — "A speculative call that errored must not end the call: it
// was a bonus attempt, so fall back to a fresh think with its own race."
if (raced && raced.err && specHit) { thinkWrapped = voice.think(call, heard)... }
```

But when the 1200ms race times out, the same speculative promise is parked as
`call.pendingThink` (`:1607`) and consumed on the redirect leg at `:1444`, where
that protection does not exist:

```js
const r = await pending;
if (r.err) { ...; return xml(res, voice.sayAndHangup("Something's glitching on my end - sorry...")); }
```

So the identical failure gets a retry on one path and drops the call on the
other — and the parked path is the *likelier* one, because a speculation
launched 600ms after the last partial is usually still running when the 1200ms
timer fires.

**I did not fix it, deliberately.** The obvious patch — retry the think on the
redirect leg — can make things worse: `think()` has a 9s cap, and a spec that
errors at 9s followed by a fresh 9s think blows straight through Twilio's 15s
window, which is a *worse* caller experience than the honest bow-out. A correct
fix needs a time budget carried across the two legs, or the ack-and-redirect
trick used a second time. That is a design decision, not a null check.

Worth doing: `call.lastThinkMs` is already recorded, so the budget is
measurable. Worth measuring first: how often `think()` actually errors in
production. If it is rare, this finding is worth nothing and should be closed.

## 5. `announceBooking` never checks the suppression list — NOT FIXED (product decision)

**`lib/notify.js:90-107`** · confidence: **high** (code is unambiguous);
exposure now small

Finding 1 closed the path that made this reachable from a do-not-call. The hole
itself is still there: `announceBooking` texts `appointment.phone`
unconditionally. Every other outbound message in the codebase checks first — the
missed-call text-back at `server.js:1979` does, the dialler does, the mailer
does. This one does not.

Remaining reachable paths are narrow (a booking taken on a line whose number is
already suppressed; the public callback form at `server.js:1191`), and the
suppression list is explicitly one list across both channels: *"anyone who opts
out is never contacted again — by email or phone."*

**The decision, and it is a real one:** should a *transactional* confirmation to
someone who booked a job with us on the phone be blocked by a marketing opt-out?
My read is yes — a single-list promise has to be single. But it is the owner's
promise to make, so I have not changed it. One `isPhoneSuppressed` check at
`lib/notify.js:90` is the whole patch, whichever way it goes.

## 6. Someone who opted out of our calls can no longer reach the business — NOT FIXED (product decision)

**`server.js:1230-1236`** vs **`server.js:1361`** · confidence: **high**

Inbound calls are rejected outright when the number is on the suppression list:

```js
// "Blocked callers (the owner's own list, plus anyone who told us to stop) are
//  rejected before a single AI token or plan minute is spent."
if (suppress.isPhoneSuppressed(account.id, params.From || '').blocked) { ...<Reject/>... }
```

131 lines later, the code logs the opposite intent — and the branch is
unreachable, because `blocked` cannot be true by then:

```js
// server.js:1361
+ (inDnc.blocked ? ' (this number is on your do-not-call list — they called you, so we answered)' : '')
```

Two intents collided and the dead log line is the fossil. They are not the same
list in spirit: *"stop calling me"* said to a cold call means stop **dialling**
me, and the one list the product keeps cannot tell that apart from *"block this
harasser"*, which must reject.

The cost of getting it wrong in the current direction: a prospect who declined a
sales call six months ago rings the plumber with a burst pipe and the line
rejects them. The owner never learns the call happened. That is a lost job and,
on a $399 plan sold as "every call answered", a bad one.

**Suggested shape** (not implemented — it is a data-model change): record *why*
a number was suppressed. `reason: 'manual'` (the owner blocked them) rejects;
`reason: 'unsubscribe'` (they asked us to stop calling *them*) answers, and the
dialler keeps honouring it. `suppressPhone` already stores the reason, so the
information exists; only the read at `:1230` throws it away.

## Smaller notes, checked and not worth a branch

- **The `dialChain` waterfall is sound.** `server.js:1877-1904`: the index
  advances only while a next number exists, a restart leaves it falling through
  to the take-a-message gather, and re-entering `transfer` resets the chain to 0
  rather than stacking. The one wrinkle is that a redelivered `/voice/dialback`
  advances `dialIdx` twice and skips a person on the on-call list — a redelivery
  needs our ack to be lost, and the consequence is one skipped tech on a
  waterfall that continues, so it is not worth the state to guard it.
- **`call.screening` clears correctly** (`server.js:1538`) and the `/voice/status`
  text-back check honours it (`:1978`), so a caller who never answers the screen
  gets no text. One asymmetry: the screening branch at `:1292` starts the call
  with `lead: null, leadBrief: ''`, so a suspect caller who turns out to be a
  real person loses their lead context for the rest of the call. Only reachable
  for a number with no call history, so the brief would usually be thin anyway.
- **A consent record can exist for an offer that never arrived.**
  `server.js:1989` writes the `offered` call-back row *before*
  `notify.sendSMS` resolves, so a text that fails to send still leaves a row
  that a later "YES" attaches to — and the stored TCPA basis then quotes an
  offer the person never received. Narrow (they would have to text YES
  unprompted) but it is the one record that exists purely as evidence, so it
  should be written only on a confirmed send.
- **`/sms/incoming:1135` treats a bare "yes" as un-suppress**, alongside "start"
  and "unstop". A suppressed number texting "yes" for any reason comes off the
  list. Unprompted and therefore rare — but "yes" is not an opt-in word and does
  not belong in that set.
- **The in-memory `calls` map still only prunes above 500 entries**
  (`lib/voice.js:320`), so a call whose status callback never arrives leaks its
  account, profile and transcript forever. Already fixed on
  `keeper/2026-10-13-voice-call-map-leak`; unmerged.
- **Billing arithmetic is otherwise clean.** `consumeVoiceMinutes` reads a fresh
  account synchronously immediately before charging, and the whole in-memory
  status path runs without an `await` from `getCall` to `endCall`, so two
  concurrent deliveries cannot interleave and double-charge. I checked for it
  specifically; it is not there.
- **`sweepStuckCalls` works** (`server.js:397`, timer at `:404`) — rows frozen at
  `in-progress` are closed after two hours whether or not the owner opens the
  tab.
