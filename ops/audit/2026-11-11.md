## 1. Parked call-backs never leave the queue: the morning batch is starved, and the old ones eventually ring

**`server.js:348`, `server.js:350`, `server.js:360`, `server.js:377-387`** ·
severity **High** · confidence **high, reproduced end to end against the running
server and the real 60-second timer** · **not fixed — see §3**

`placeCallback` has one status, `queued`, for two completely different things:

```js
// server.js:353-357 — "wait until the morning": self-clearing, has a dueAt
const hours = callback.withinCallingHours(voice.tzFor(account));
if (!hours.ok && by !== 'owner') {
  const dueAt = callback.nextCallingWindow(voice.tzFor(account));
  db.updateCallback(rec.accountId, rec.id, { status: 'queued', dueAt, note: hours.reason });

// server.js:348 — "this account cannot place calls at all": nothing clears it, NO dueAt
if (!plan.ok) { db.updateCallback(rec.accountId, rec.id, { status: 'queued', note: plan.reason }); ... }
```

The three standing blockers — no paid plan (`lib/plans.js:402`), a plan with no
phone minutes (`:406`), no number yet (`server.js:350`), no profile
(`server.js:360`) — all park the row as `queued` **with no `dueAt`**, which the
queue reads as *due right now, on every tick, for ever*:

```js
// server.js:377-387
async function runCallbackQueue() {
  let due = [];
  try { due = db.readCollection('callbacks').filter((c) => c.status === 'queued' && (!c.dueAt || Date.parse(c.dueAt) <= Date.now())); } catch { return; }
  for (const rec of due.slice(0, 20)) {
```

Three things follow, and the first is the one that costs money.

### 1a. Twenty permanently-parked rows starve every tenant's queue, for ever

`readCollection('callbacks')` is **global across tenants** and the array is in
insertion order, so `due.slice(0, 20)` is *the twenty oldest due rows on the
whole install*. Rows that can never clear are the oldest, so they hold all
twenty slots on every tick and nothing behind them is ever reached.

The starved population is specific, and worth being precise about: a request
made **during** calling hours is dialled directly by the form
(`server.js:1013`) and by the SMS-YES path (`server.js:1158`), so those still
work. What goes through the queue is **the overnight batch** — the 11pm form
submission the page promises *"will ring you first thing"* — plus anything
parked by a blocker that later clears. That is exactly what is starved.

A trial account is enough to do it. It signs up, opens the call-backs tab
(which mints the form slug), tests its own form once — and that row is parked
`"Phone calling needs a paid plan."` for ever. Twenty of those anywhere on the
install, from any tenants, and every paying Front Desk customer's morning
call-backs stop going out, silently, with the rows still showing `queued` in
their UI.

**Reproduced** (`node ops/audit/2026-11-11-repro-queue.js`, real server on
port 8131, real 60-second timer, Twilio's REST call stubbed to record what it
would have dialled — the script is committed next to this report):

```
== PHASE 0: a real form submission on an account that cannot call ==
  form POST -> 200; page promises: "ring you first thing — from 9am (CST)."
  row status: queued   note: "Phone calling needs a paid plan."
  dueAt: undefined   -> due on every tick: true

== PHASE 1: 20 parked rows ahead of a paying tenant in the GLOBAL queue ==
  rows due this tick: 24 (queue dials at most 20/tick, oldest-first by insertion)
  position of the paying shop's overnight request in that list: 23
  waiting for one 60s queue tick...
  dials placed by the tick: 0
  paying shop's overnight row status: queued
  callbacks.json full rewrites during the tick: 20
  => STARVED: the paying tenant's due call-back was NEVER DIALLED

== PHASE 2: an operator clears the 20 parked rows. Next tick: ==
  dials placed: 2 -> ["+13125559911","+13125559922"]
```

Nothing anywhere clears a parked row: I checked every `updateCallback` call site
(`server.js:336,339,341,344,348,350,356,360,368,372,1153`) and `callbacks.json`
is the collection `lib/db.js:34` calls *"never pruned"* — there is no reaper, no
attempt counter, and no cancel or dismiss action in the API
(`server.js:3152-3191`). The owner can see the rows and their notes; they cannot
clear them.

### 1b. When a blocker does clear, requests from weeks ago ring people

`callbackAllowed` enforces a 90-day limit for the owner-initiated source
(`lib/callback.js:85-86`) and **no age limit at all for the form source**
(`lib/callback.js:67`). Verified directly: a 400-day-old form consent returns

```
{"ok":true,"basis":"they asked on the web form and ticked the consent box"}
```

and in the reproduction above a **45-day-old** request was dialled as soon as
the queue reached it (`ancient (45 days old): called`).

**The trigger is dated, recurring, and needs nobody to do anything.** Voice
usage resets on the month boundary by itself:

```js
// lib/plans.js:353
if (pro && account.voicePeriod !== periodKey()) vUsed = 0;   // periodKey() is UTC YYYY-MM
```

Verified in isolation — the same exhausted Front Desk account, differing only in
`voicePeriod`:

```
voicePeriod last month -> {"ok":true,"remaining":500}
voicePeriod this month -> {"ok":false,"reason":"You've used all 500 phone minutes this month..."}
```

So: a Front Desk shop burns its 500 minutes on the 20th. Every form request for
the rest of the month is parked `queued`. At 00:00 UTC on the 1st the plan gate
flips open; the first tick after that re-stamps the whole backlog through quiet
hours onto the next local 9:05am (confirmed in the reproduction: a 30-day-old
row came back `dueAt 2026-11-11T15:05:00.000Z`, 9:05 Chicago) — and at 9:05am
on the 1st the AI dials the backlog, twenty a minute, opening with

> *"You asked us to call you back about [thing], so here I am."*

to people who asked days or weeks ago. It bills the new month's minutes
immediately (~2 min each, so 60 stale requests is ~120 of the 500) and costs
real Twilio money at ~$0.16–0.21/min per COST.md. The consent is on file and the
product calls these informational, so this is not me calling it illegal — but
the same code enforces 90 days when the *owner* clicks call-back, and the FCC
cares about whether a consent is still current. The product harm needs no legal
argument: it is the single most embarrassing thing this feature can do.

### 1c. The owner is told it failed, and it rings later anyway

`server.js:3189` → `placeCallback(rec, { by: 'owner' })`. The owner path skips
quiet hours and the once-a-day rule, but **not** the plan gate, so an owner who
clicks "call back" with no minutes left gets `400` and an error toast
(`queued` is only set on the quiet-hours branch, so the response says `queued:
false`) — while the row is parked `queued` and will be dialled whenever minutes
free up. They were told it did not happen.

## 2. The double-dial last week asked about is real, and already fixed on an open branch

Last week nominated: *"worth checking whether a tick that overruns 60s can
double-dial"*. It can, the mechanism is exactly as suspected, and
`keeper/2026-10-12-callback-queue-reentrancy-lock` (open, unmerged) is a correct
fix. I read the diff rather than trusting the name.

A row only leaves `queued` **after** `await voice.placeCall` resolves
(`server.js:362` → `:368`), so it stays `queued` for the whole Twilio round
trip. `voice.placeCall` allows 15 seconds (`lib/voice.js:907`), the tick
processes up to 20 rows serially, and the re-read guard at `server.js:381-383`
reads the row *before* that await — so a tick still working when the next one
fires hands the same still-`queued` row to a second `placeCallback`, and the
person is called twice. The branch adds a `callbackQueueRunning` flag with a
`finally` reset; the inner `catch { return; }` still runs the `finally`, so the
flag cannot stick on. **Nothing to add. Merge it.**

I did not re-implement it, and I did not write a suite for it: that would
duplicate an open branch, which is what 09-09 and 09-30 both flagged as the
failure mode of this routine.

## 3. What I shipped, and what it does not do

**`audit/2026-11-11-skip-noop-callback-writes`** · 1 file changed in `lib/db.js`
(9 lines), plus `test-callbackwrites.js` (20 assertions, 4 of them failing on
`main`).

The reproduction surfaced this: **20 full rewrites of `callbacks.json` per tick,
for ever**, to write back the status and note each parked row already had.
`updateCallback` (`lib/db.js:534`) wrote unconditionally. At one tick a minute
that is 28,800 whole-file rewrites a day of the one collection that is never
pruned and holds every consent record, and each one blocks the event loop the
live voice webhooks share — the amplifier last week's §1 measured.

The fix writes only when a value actually changes. It is behaviour-identical:
the row ends up the same either way, any real change still writes exactly once,
and the write-once consent rule above it is untouched (a patch that only tries
to rewrite locked evidence now writes nothing instead of writing an unchanged
file). `node --check` clean on both files; all six existing suites green
(voicebilling 7, voiceprofiles 17, spam 18, reps 37, sending-mode 9,
assistant 15).

**This is not the fix for §1.** It makes the broken retry loop cost nothing. The
rows are still parked, still starving the queue, still waiting to ring someone
about a month-old request.

## 4. Not implemented, deliberately

§1 needs a product decision, which this brief says to describe rather than ship.
Three decisions, in the order I would ask them:

1. **How old is too old for a form request?** The code already answers this for
   the owner source: 90 days (`lib/callback.js:86`). For a form that promises a
   call "in the next minute", the honest number is hours, not weeks. Whatever it
   is, `callbackAllowed` is the right place — one line, and it fails closed like
   the rest of that function.
2. **Should "cannot call at all" share a status with "waiting for 9am"?** It
   should not. A distinct non-dialable status (`parked`) keeps those rows out of
   `due` entirely, which fixes the starvation outright — but then something has
   to put them back when the blocker clears (a number is bought, a plan is
   upgraded, minutes reset). That re-entry trigger is the design work, and it is
   where I would spend the hour.
3. **Should the per-tick budget be per-account?** Twenty per tick globally is
   also what lets one tenant's backlog delay another's. Per-account fairness is
   a bigger change than either of the above and I would do it last.

A cheap interim that needs no decision beyond "yes": give the owner a way to
dismiss a row in `/api/callbacks`, so a human can at least unjam the queue.

Also noted and not acted on, because the trigger is too narrow to call a finding:
`sweepStuckCalls` (`server.js:397`) only looks at each account's newest 50 calls
(`db.getCalls(accountId, 50)`), so a row stuck `in-progress` could in principle
be pushed out of view before the 2-hour threshold makes it sweepable — it needs
50+ calls on one line inside two hours, which no real tenant on a 500-minute
plan does.

## 5. Checked and clean

Recorded so a later run need not redo them:

- **No double-billing on the outbound leg.** A call-back's minutes are billed
  once by `/voice/status` (`server.js:1947-1949`), idempotently against
  `billedMin`, and the restart fallback (`server.js:1911-1932`) only fires when
  the in-memory call is already gone. The 10-07 fix is on `main` and holds for
  outbound.
- **Opt-out on an outbound call-back works.** `out.action === 'dnc'`
  (`server.js:1649-1651`) suppresses `call.to` for outbound, and
  `placeCallback` checks the suppression list before dialling
  (`server.js:340-341`), so "stop calling" also kills every other queued row
  for that number on that account.
- **Call length is bounded.** The time and exchange caps (`server.js:1548-1580`)
  are checked on every heard turn; silence hangs up at three empty gathers
  (`server.js:1507`) and the noise-replay branch can only fire once per turn
  (`call.replayAt`), so neither silence nor a loud room can hold a line open.
- **No intermediate-status hazard.** `voice.placeCall` sets no
  `StatusCallbackEvent` (`lib/voice.js:889-905`), so Twilio posts
  `/voice/status` only on completion — the handler's unconditional
  `voice.endCall(sid)` cannot destroy a live call's state.
- **The answer-webhook race is not reachable in practice.** `startCall`
  (`server.js:364`) runs after `await placeCall`, but `MachineDetection:
  'Enable'` with `AsyncAmd: 'false'` makes Twilio finish answering-machine
  detection before it requests `/voice/answer`, so the in-memory record is
  always registered first.
- **A voicemail-drop costs money and bills no plan minutes**
  (`server.js:1391`, then `callerSpoke` is false at `:1941`). Correct for
  inbound dead air; on an outbound call-back it is a small deliberate margin
  leak, not a bug. Noted for COST.md, not fixed.
