## Finding 1 — the send lock expires healthy jobs, and the duplicate it prevents is the one it causes

**`server.js:443-450` (the lock), `:458` (the snapshot), `:511-601` (the loop)** ·
severity **High** · confidence **high, reproduced**

### What the code says it is for

The lock's own comment, at `server.js:434-437`, states the failure exactly:

```js
// One send job per account at a time. Without this, a second click or a page
// reload starts a concurrent run over the same approved queue items and every
// recipient gets the email twice.
```

### What the staleness check underneath it actually does

```js
// server.js:447-450
// Also treat a job with no progress for 10 minutes as dead rather than live.
if (runningJob && runningJob.status === 'running' && Date.now() - (runningJob.startedAt || 0) > 30 * 60 * 1000) {
  runningJob.status = 'error'; runningJob.error = 'Timed out'; activeSends.delete(account.id);
}
```

The comment says **no progress for 10 minutes**. The code measures **total age against 30
minutes**, and there is no progress signal in the expression at all. Those are different
predicates, and the difference is the bug.

A healthy send is slow on purpose. `server.js:591`:

```js
const baseSec = Math.max(60, Number(account.sendDelaySec ?? 180));
```

paced by `sending.nextDelayMs(baseSec, baseSec * 2.5)` — a uniform **180-450s gap between
every email** at the default. So a normal run passes 30 minutes somewhere around the
**sixth** email, and stays "stale" for the rest of its life. Default `dailyCap` is 50. In
other words the check does not catch the rare wedged job; it catches essentially **every
real job**.

### The chain

1. Customer approves 30 drafts and clicks Send. Job A starts. `activeSends` holds its id.
2. ~35 minutes later A has sent about 6 and is asleep in its pacing gap. The UI shows
   "6 of 30".
3. Customer clicks Send again — impatient, or a second tab, or the one-button send path.
4. `startSendJob` runs. A is older than 30 minutes, so A is marked `status = 'error'` and
   **the lock is released**.
5. The guard below it (`server.js:451`) only throws when the running job's status is still
   `'running'`. It was just changed to `'error'`, so it does not throw. Job B starts.
6. B's snapshot is `db.getQueue(...).filter((q) => q.status === 'approved')` (`:458`). The
   24 drafts A has not reached are still `approved`, so they are all in B's list.
7. **Nothing stopped A.** Grepping every write: `stopRequested` is set in exactly one place,
   `/api/send/stop` at `server.js:3473`. The force-expiry path does not touch it. A's loop
   reads only `job.stopRequested` (`:594`, `:597`, `:601`), so it wakes from its sleep and
   carries on.
8. Both loops now walk the same 24 items. The loop body checks lead sendability (`:514`)
   and suppression (`:526`) but **never re-reads `it.status`**, so neither notices the
   other. Every one of those 24 people gets the same email twice.

### Reproduction

I lifted `server.js:443-457` verbatim into a harness with a virtual clock and SMTP stubbed:

```
second startSendJob threw : NO — a new job started
jobA.status after          : error
jobA.stopRequested         : false
jobB items (still approved): b@example.com, c@example.com

smtp.sendMail calls:
  jobA -> a@example.com
  jobA -> b@example.com
  jobA -> c@example.com
  jobB -> b@example.com
  jobB -> c@example.com

DUPLICATE recipients: b@example.com, c@example.com
```

### Why this one matters more than it looks

AUDIT.md #15 calls deliverability "your existential risk", and the whole send path is built
around that belief — warmup ramps, randomised pacing, a hard daily cap, SPF/DKIM/DMARC
gating, suppression at the send boundary. Sending the same cold email twice, minutes apart,
from a warming domain is close to the worst single thing that path can do. It also burns
double the daily cap, so the warmup ramp the code so carefully computes is wrong for that
day.

And it is silent. The duplicate lands in the recipient's inbox, not in any log the owner
reads. `db.logSend` records both as normal sends.

### The fix — pushed on `audit/2026-09-23-send-lock-duplicate`

Three changes, layered so that no single one is load-bearing:

1. **Measure staleness from progress, not age.** `lastProgressAt` is stamped at the top of
   each loop iteration and the check compares against that. "Dead" now means what the
   comment always said. A genuinely wedged job is still expired: the longest legitimate gap
   between two iterations is one pacing sleep (450s) plus one send timeout (90s), i.e. 9
   minutes, comfortably inside 30.
2. **Set `stopRequested` when force-expiring.** Marking a job `'error'` only relabels it.
   If a wedged job ever does wake up, it now halts instead of sending beside its
   replacement.
3. **Re-read the queue item before each send**, and skip anything no longer `approved`.
   This is the one that actually closes the window — including the residual race where the
   old loop is mid-`sendMail` at the moment the new snapshot is taken.

Change 3 fixes a second bug for free. `/api/queue/adjust` (`server.js:3418`) rewrites drafts
and sets them back to `status: 'pending'`. It can run while a send is in flight, and the
running job holds an hours-old snapshot — so "rewrite these, they're too long" would put the
**old** copy on the wire and mark it sent, with the customer watching the new copy sit in
the queue. Now it is skipped and counted.

Counted as `changed`, not `skipped`: `skipped` already means "over today's cap" and carries
`capReason` to explain it to the user. Conflating them would make that explanation lie.

Verified on the patched code, again with the lock logic lifted verbatim:

```
job age                   : 33 min
minutes since progress    : 6
second click on a live job: REJECTED — "A send is already running for this account."
live job still running    : true | told to stop: false
emails on the wire        : 10 | duplicates: none

wedged job replaced       : yes
wedged job told to stop   : true
emails on the wire        : 10 | duplicates: none

after mid-run rewrite     : sent 2 | skipped as changed: 8
```

`node --check server.js` clean; `node test-sending-mode.js` 9 passed, 0 failed.

## Finding 2 — request bodies are decoded one TCP chunk at a time

**`server.js:74-87`** · severity **High** · confidence **high, reproduced**

```js
// server.js:77-80 — before
let b = '';
req.on('data', (d) => {
  if (over) return;
  b += d;
```

`d` is a `Buffer` — nothing calls `req.setEncoding()` anywhere in the file. `b += d`
therefore invokes `d.toString()` on **each chunk independently**. A UTF-8 character is 1-4
bytes, and a chunk boundary falls wherever the network puts it, so any multi-byte character
straddling two reads is decoded as two invalid fragments and comes out as U+FFFD.

This is not a corner case. Chunk boundaries track TCP segments, so **any body past roughly
1400 bytes routinely spans chunks** — a profile save, a CSV paste, a Stripe event.

### Reproduction

A JSON body split mid-emoji, against the real `readBody`:

```
sent  : {"name":"café — naïve 😀"}
got   : {"name":"café — naïve ���"}
equal : false
```

The JSON still parses. The data is just quietly wrong.

### Where it costs money

`/webhook/stripe` (`server.js:2215-2221`) is the one that matters:

```js
const raw = await readBody(req);
const event = stripe.verifyWebhook(raw, req.headers['stripe-signature']);
if (!event) return json(res, { error: 'bad signature' }, 400);
```

The signature is an HMAC over these exact bytes. Corrupt one and a **genuine Stripe event
verifies as a forgery** and is answered 400 — so the subscription change it carried is
dropped. Stripe retries, but every retry re-delivers the same payload over a fresh
connection, which can split at a different place or the same one. Whether it ever gets
through is luck.

Stripe payloads carry customer names, addresses, product and price descriptions — plenty of
places for a non-ASCII byte to sit. A `customer.subscription.deleted` lost this way leaves
a churned customer with full access; a `checkout.session.completed` lost this way leaves a
paying customer locked out. There is a reconcile-on-return path at `server.js:2308` that
rescues the second case, which is probably why this has not surfaced as a support ticket.

The Twilio webhooks are safe by accident: form-encoded bodies are percent-escaped, so they
are pure ASCII on the wire.

### The fix — pushed on `audit/2026-09-23-readbody-utf8`

Keep the chunks as Buffers, `Buffer.concat` them, decode once at the end. The 2MB flood
guard now counts bytes instead of decoded characters, which is what `MAX_BODY` meant anyway.

Verified: the split-emoji body round-trips byte-identical and its HMAC matches; a 3MB body
is still cut off; a normal small body is unchanged.

```
sent  : {"name":"café — naïve 😀"}
got   : {"name":"café — naïve 😀"}
equal : true
stripe signature matches : true
```

## Reported, not fixed

Each of these needs a product call, so I have left them alone.

### 3. The daily cap can be spent twice in one calendar day — Medium

`server.js:460` captures `const todayStr = db.today()` once, at job start, and the loop
stamps `sentToday: { date: todayStr, count }` on every send (`:567`). A 50-email run takes
about 4.5 hours at default pacing, so a job started in the evening crosses midnight and
keeps writing **yesterday's** date. A job started after midnight then reads
`account.sentToday.date === todayStr` as false (`:461`), treats `sentToday` as 0, and grants
a fresh full cap — while the first job is still sending against the same day.

Net: up to **2x the daily cap** in one calendar day, on a domain whose warmup allowance was
computed on the assumption of 1x.

Not fixed because the correct behaviour is a decision, not a bug fix: when a run crosses
midnight, does it keep the allowance it was granted, or re-derive `cap` and `allowed`
against the new day mid-loop? Both are defensible; they are different products. Note
`db.today()` (`lib/db.js:51`) is server-local, so "midnight" is Render's clock, not the
customer's.

Partial mitigation exists: `sending.withinBusinessHours` defers most leads overnight. It
does not help accounts on `sendWindow: 'anytime'`, or lists with non-US leads whose local
hours are open at US midnight.

### 4. `/v1/calls` filters `since` after it truncates — Medium-low

```js
// server.js:2240
const rows = db.getCalls(keyAcc.id, lim).filter((c) => !since || Date.parse(c.at) >= since)...
```

`db.getCalls(id, limit)` (`lib/db.js:197`) returns the newest `limit` calls, and the `since`
filter runs on that slice. An integration polling `?since=<last seen>` to sync into a CRM
gets at most the newest `lim` calls; anything older than that within the window is dropped
permanently, because the API offers no cursor to page backwards. A customer who takes more
than 100 calls between polls silently loses the rest.

`/v1/bookings` (`server.js:2236`) has a related shape: `db.getAppointments()` sorts by
`startsAt || createdAt`, the `since` filter runs on `createdAt`, and `.slice(-lim)` then
keeps the rows with the **latest appointment times** rather than the latest creation times.
A booking made now for tomorrow can be dropped in favour of one made yesterday for next
month.

Not fixed: correcting either changes documented response semantics for whatever integrations
already exist. It wants a cursor (`after=<id>`), which is an API design decision.

### 5. `/u/` unsubscribes on a GET, so link scanners unsubscribe people — Low

`server.js:1998-2001` treats GET and POST identically. The POST is RFC 8058 one-click and is
correct. The GET is the footer link — and corporate link scanners (Microsoft Defender Safe
Links, and most security gateways) fetch every URL in an inbound message. Those fetches
unsubscribe the recipient without any human ever clicking, and the owner sees a lead go
quiet with `Unsubscribed: <email>` in the activity log looking like a real opt-out.

The conventional fix is a confirmation page on GET with a POST button, keeping the
one-click POST as-is. Not fixed because adding a click to an unsubscribe is a compliance-
adjacent judgement I should not make unilaterally.

### 6. The free-autofill counter is a lost update — Low

`server.js:2357` does `db.updateAccount(account.id, { autofillsUsed: Number(account.autofillsUsed || 0) + 1 })`
against the `account` object read at the top of the request. Two concurrent autofills both
read the same value and both write the same increment, so a locked account gets a third free
autofill. Same read-modify-write shape as the 2026-09-02 finding in `lib/plans.js`. Costs
pennies; listed only because it is the same pattern and will be fixed by the same helper if
one is ever written.

## Checked and sound

Things I went through under this lens and found correct, so a future run need not re-derive
them:

- **`/voice/turn`'s acknowledgment/redirect leg** (`server.js:1388-1397`, `:1550-1573`).
  The `pendingThink` handoff is intricate and I expected trouble. It is right: `heard` is
  scoped to the `out === null` block and never read outside it (no `ReferenceError` on the
  redirect leg), the pending promise is always pre-wrapped into `{v}`/`{err}` so an
  abandoned one cannot become an unhandled rejection, and a stray `SpeechResult` on the
  redirect leg falls through to a fresh think rather than mixing states.
- **Speculation** (`server.js:416-430`). `specCount` caps it at one per turn, the shallow
  `view` genuinely avoids mutating `call.turns`, and the result is used only on an exact
  `normSpeech` match.
- **Twilio signature verification** on both `/sms/incoming` and `/voice/*`, including the
  proxy-header URL reconstruction. Verified before any state is touched in both.
- **Spam/screening state machine** in `/voice/turn`. `call.spamCall` is set before every
  `spam.strike` so `/voice/status` cannot strike the same call twice, and the screening
  branch's tighter silence leash does not leak into the normal path.
- **The `RANK` urgency comparison** (`server.js:1605-1606`). `RANK[undefined] || 0` looks
  like a bug and is not, because `routine` is deliberately 0.
- **The outer error handler** (`server.js:3579-3596`). Voice and SMS paths never emit a 500,
  so Twilio never speaks "an application error has occurred" to a caller.
- **`job.done` accounting** in the send loop. Five exit paths through the loop body — held,
  suppressed, deferred, sent, threw — each incrementing exactly once. No double-count, no
  path that skips it.
- **`/api/` paywall list** (`server.js:2336-2354`). Every entry in `READ_ONLY` is genuinely
  read-only or a door-out (stop, cancel, release a number), which is the right call.
- **`parseCSV`** (`server.js:107-119`). Quote handling, the doubled-`""` escape, CRLF, and
  the trailing-field case are all correct.
- **Rate limiter arithmetic** (`server.js:124-135`). Off-by-one checked: `max` requests
  pass, the `max + 1`th is limited.
