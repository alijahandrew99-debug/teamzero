## 1. A password reset did not sign out any other device — FIXED

**`server.js:2226-2232`** · severity **Medium-High** · confidence **high,
reproduced** · branch `audit/2026-10-14-reset-invalidate-sessions`

`lib/db.js:152-158` defines, and `:608` exports:

```js
// Sign out every device for an account (used after a password reset).
function destroyAllSessions(accountId) {
```

It is called from **nowhere**. `grep -rn destroyAllSessions --include=*.js .`
returns exactly two hits: the definition and the export line.

The reset handler changed the password and issued a new cookie, and that was all:

```js
// server.js:2226-2232 — before
const accountId = db.useResetToken(f.token);
if (!accountId) return fail('That reset link has expired or already been used. Request a new one.');
const { salt, passHash } = auth.hashPassword(f.password);
db.updateAccount(accountId, { salt, passHash });
db.logActivity(accountId, { agent: 'SYSTEM', msg: 'Password reset' });
const token = db.createSession(accountId);
```

Sessions live **30 days** (`lib/db.js:112`), and `getSession` only checks `exp`
(`:116-122`) — never the password, never a version counter. So every session minted
before the reset keeps working for up to a month after it.

### Failure scenario

This inverts the purpose of the feature. Nobody resets a password for fun — they do
it because they believe someone else is in their account. Concretely: a shop owner
signs into Dawnpipe on a laptop they then sell, lend, or have stolen; or a former
employee's browser still holds the cookie; or a cookie is lifted off a shared
machine. The owner does the one thing the product offers for this — "Forgot
password?" → reset — and the app tells them they are safe. The activity log says
`Password reset`. The other party's cookie keeps working, for up to 30 days, with
full access to the account: customer PII in `leads`, call recordings and
transcripts, the connected mailbox, the Stripe billing portal, and the ability to
send mail as them.

The person with the most reason to think they are protected is the one who is not.

### Reproduced

Against the real `lib/db.js` with an isolated `DATA_DIR`:

```
before reset:
  attacker session valid : true
after password change WITHOUT destroyAllSessions:
  attacker session STILL valid: true   <-- the bug
after destroyAllSessions + new session:
  attacker session valid : false
  victim old session valid: false
  freshly issued session  : true (must be true)
  OTHER tenant untouched  : true (must be true)
RESULT: PASS
```

### The fix

One call, placed between the password write and the new `createSession` — order
matters, or it kills the cookie it is about to hand back:

```js
db.destroyAllSessions(accountId);
db.logActivity(accountId, { agent: 'SYSTEM', msg: 'Password reset — all other devices signed out' });
const token = db.createSession(accountId);
```

`node --check server.js` clean. All six repo suites pass — **103 assertions, 0
failures**. The log line now states what happened, because "Password reset" on its
own is what made the gap invisible.

**Related, not fixed (deliberately — keeping the branch single-purpose):**
`useResetToken` (`lib/db.js:143-151`) is single-use for *its own* token but does not
drop the account's **other** outstanding reset tokens. Request three reset emails
and all three stay valid for an hour; using one does not kill the rest. Same class
(a stale credential surviving a reset), smaller blast radius, and it belongs with
`keeper/2026-08-30-prune-reset-tokens` rather than in this branch.

## 2. Rate limiting and TCPA consent evidence both trust a header the client sets — NOT fixed

**`server.js:134-137` and `server.js:1000`** · severity **Medium-High** ·
confidence **high on the code, unverified on the production proxy** · needs one
measurement, not a patch

```js
// server.js:134-137
function rateLimited(req, bucket, max, windowMs) {
  const ip = (req.headers['x-forwarded-for'] || '').split(',')[0].trim()
    || req.socket.remoteAddress || 'unknown';
  const key = `${bucket}:${ip}`;
```

The rate-limit key is the **leftmost** entry of `X-Forwarded-For`. The leftmost
entry is the one furthest from the server — i.e. the one the *client* wrote. The
standard proxy idiom (nginx `$proxy_add_x_forwarded_for`, which is what Render's
load balancer does) **appends** the real peer address to whatever the client sent,
so a request carrying `X-Forwarded-For: 1.2.3.4` arrives as
`1.2.3.4, <real client IP>` and this code reads `1.2.3.4`.

If that is how Render behaves, every throttle in the app is bypassed by rotating one
header value per request:

- `/login` — 10 per 15 min (`:2274`) → unlimited password guessing. Passwords have a
  **6-character** minimum (`:2246`), so this is the throttle that was doing the work.
- `/signup` — 20 per hour (`:2240`) → unlimited trial farming. AUDIT.md calls
  unmetered usage a CRITICAL margin hole, and each trial is 15 real AI-researched
  leads that cost money.
- `/forgot` — 5 per 15 min (`:2184`), `/cb/:slug` — 20 per hour (`:988`),
  `assistant` — 40 per 6h (`:3112`), `adjust` — 20 per hour (`:3476`).

This is AUDIT.md item #7 ("Rate limiting — DONE") being structurally undone.

**The same expression is the TCPA consent record**, which is worse in kind if not in
degree:

```js
// server.js:1000
const ip = String(req.headers['x-forwarded-for'] || req.socket.remoteAddress || '').split(',')[0].trim();
// ...stored at :1003 as consentIp
```

`lib/db.js:30-35` describes `callbacks.json` as *"the evidence... their IP —
unaltered, append-only, never pruned"*, held because the burden of proving consent
under the TCPA is on the caller. An IP the submitter chose is not evidence of
anything. The consent record is only as good as its weakest field, and this is a
field the form-filler controls.

### Why I did not patch this

The obvious fix — read the **rightmost** entry instead — is correct only if exactly
one trusted proxy sits in front. Get the depth wrong in the other direction and
every request keys on the load balancer's own address, which collapses all customers
into one bucket and locks the whole tenant base out of `/login` after ten attempts.
That is a production outage caused by a security fix, which is not a trade I will
make unprompted on a live revenue app.

It needs one measurement first: log the raw `X-Forwarded-For` on one request in
production and count the entries. Then take the Nth-from-right, with the proxy depth
as an explicit env var (`TRUSTED_PROXY_HOPS`) rather than a guess in the code. Once
that exists, the same helper should serve both call sites and the two SSRF-adjacent
spots noted in 09-16.

I could not take that measurement myself: this environment's network policy blocks
dawnpipe.com (the proxy returns 403 on CONNECT), and every rate-limited route is
either a POST or authenticated, both of which the brief forbids against production.
So the code reading is solid and the production behaviour is one `console.log` away
from certain.

## 3. `/v1/*` scans every account on an unauthenticated request, with no throttle — NOT fixed

**`server.js:2305-2310`** · severity **Low-Medium** · confidence **high**

```js
if (p.startsWith('/v1/')) {
  const bearer = String(req.headers.authorization || '').replace(/^Bearer\s+/i, '').trim();
  const keyAcc = bearer && bearer.startsWith('dp_live_') ? db.allAccounts().find((a) => a.apiKey === bearer) : null;
  if (!keyAcc) return json(res, { error: 'Invalid or missing API key...' }, 401);
  if (rateLimited(req, 'apikey:' + keyAcc.id, 600, 60 * 60 * 1000)) ...
```

The throttle is keyed on `keyAcc.id`, so it can only run **after** a key matches.
A *wrong* key is never rate-limited at all. And each attempt calls
`db.allAccounts()` → `fs.readFileSync` + `JSON.parse` of the whole `accounts.json`
(`lib/db.js:57-65, 81`), synchronously, on the event loop, before any
authentication.

This is the same shape as the still-unmerged 09-09 finding
(`audit/2026-09-09-voice-webhook-log-flood`): an unauthenticated stranger makes the
server do a full store parse per request. `/v1/*` sits above the auth gate at
`:2331`, so no session is needed. At 200 customers that is a blocking parse per
request with no ceiling, and live voice calls share the same event loop.

Key guessing itself is not the risk — `dp_live_` + 48 hex chars is not brute-forcible.
The cost asymmetry is. The fix is a per-IP throttle *before* the lookup (which
depends on finding 2 being sound first) and an index or short-lived cache instead of
a full scan.

**Noted, not a finding:** the key comparison at `:2307` is a plain `===` rather than
`timingSafeEqual`. Remote timing attacks against a 48-hex-character secret through
V8 string comparison and a network are not realistic; mentioning it only so a future
run does not re-derive it.

## Checked and clean

Listing these so a future run knows what it can skip.

- **Tenant isolation at the data layer is genuinely sound.** Every mutator filters on
  `accountId` *and* `id`, not just `id`: `updateAccount:96`, `updateProfile:410`,
  `deleteProfile:418` (with a correctly scoped cascade to leads and queue),
  `updateLead:493`, `updateQueueItem:563`, `updateCallback:534`,
  `updateAppointment:390`, `removeSuppression:183`, `saveProfileVoice:258`. I read
  each one rather than sampling. No IDOR available by substituting another tenant's
  record id.
- **No mass assignment anywhere.** This was my main hypothesis going in, since the
  mutators take a free-form `patch`. Every handler that reaches one builds the patch
  from an explicit allowlist: `/api/profile/save` (`:2518-2520`, 12 named fields),
  `/api/appointments/update` (`:2603-2606`, 3 named fields), and all 18
  `updateAccount` call sites in `server.js` pass object literals. A customer cannot set `tier`,
  `plan`, `subStatus`, `leadsUsed`, `voiceMinutesUsed` or `apiKey` on themselves.
- **Owner gating is complete.** All **12** `/api/admin/*` handlers carry
  `if (!stripe.isOwner(account)) return … 403` as their first statement — verified
  individually at `:3034, 3094, 3175, 3192, 3200, 3224, 3239, 3245, 3251, 3257, 3265,
  3312`. `isOwner` (`lib/stripe.js:41-45`) fails **closed**: an unset `OWNER_EMAILS`
  yields an empty list, so nobody is owner.
- **No state-changing GET.** I checked all 50 `method === 'GET'` routes for mutation;
  the only writes behind a GET are `/u/` unsubscribe (which is HMAC-gated and
  intentionally GET-able for mail-client footers). With `SameSite=Lax` on the session
  cookie, that closes CSRF without tokens — the cross-site POST never carries the
  cookie, and there is no GET to aim at instead.
- **`/reset`'s token reflection is not XSS.** `server.js:2219` interpolates the
  query-string token into `value="__TOKEN__"` (`views/reset.html:28`) stripping only
  `"`. Inside a double-quoted attribute that is sufficient — `<`, `>` and `'` are
  inert there. (A token of `$'` does abuse `String.replace`'s replacement-pattern
  expansion to duplicate the rest of the page into the attribute, but the inserted
  bytes are the page's own HTML, so there is no injection. Cosmetic; not worth a
  branch.)
- **No secret reaches a log or a response.** I grepped every `logActivity`,
  `console.*` and JSON response for credential interpolation. `:3383` logs
  `v.error` from the mailbox live-check (a connection error, not the password),
  `:2206` logs a send failure, `:3674` prints price ids and only whether
  `STRIPE_SECRET_KEY` is set. `/api/state` still masks the mailbox password and
  Hunter key to booleans.
- **`hooks.emit` SSRF is real but thin** (`lib/hooks.js:36-51`). URLs are
  customer-supplied and filtered only to `^https://`, so `https://127.0.0.1:port`
  or a link-local address is reachable. But it is fire-and-forget: no response body
  is ever returned to the caller, only the HTTP **status code** lands in the activity
  log (`:49`). That is a blind status-code oracle, requiring an authenticated account,
  against a host with no metadata service on https. Worth folding into the same
  IP-range check as finding 2 if that ever ships; not worth its own work.
