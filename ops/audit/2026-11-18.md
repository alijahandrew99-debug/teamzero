## 1. "Do-not-call is absolute" is one click, and nothing else remembers the opt-out

**`server.js:3363-3366`** (`/api/suppression/remove`), **`lib/suppression.js:70`**
(`unsuppress`), **`lib/callback.js:66`** (`optedOut`), **`views/app.html:1708,1718`** ·
severity **High** · confidence **high, reproduced end to end** · **not fixed —
needs a product decision, see §1d**

Repro committed at `ops/audit/2026-11-18-repro-dnc.js`. It runs in a throwaway
`DATA_DIR`, places no calls, and drives the real modules.

### 1a. The handler

```js
// server.js:3363-3366
if (p === '/api/suppression/remove' && req.method === 'POST') {
  const f = parseJSON(await readBody(req));
  return json(res, { ok: suppress.unsuppress(acc, f.email) });
}
```

That is the whole handler. `unsuppress` is equally short:

```js
// lib/suppression.js:70
function unsuppress(accountId, email) { return db.removeSuppression(accountId, norm(email)); }
```

No check on *why* the entry is there. The suppression list carries a `reason`
(`lib/suppression.js:16-21`) — `unsubscribe`, `bounce`, `complaint`, `manual` —
and this path deletes any of them identically. Its own module header says the
opposite, in the first paragraph:

> *"an unsubscribe, a hard bounce, or a manual block means that address is
> done, **permanently**, across every profile in the account … Suppression is
> also a legal requirement (CAN-SPAM: honour opt-outs within 10 business days;
> GDPR/PECR: immediately)."*

### 1b. The phone half is the part that costs real money

Phone numbers live in the same list, keyed `<digits>@phone.invalid`
(`lib/suppression.js:93-102`). So the rows this handler can delete include:

| How it got there | Written by |
|---|---|
| Caller texted STOP | `server.js:1131`, `suppressPhone(..., 'unsubscribe', { note: 'texted STOP' })` |
| Caller said "stop calling" mid-call | `out.action === 'dnc'` → `suppressPhone` |
| Recipient clicked unsubscribe in an email, and we extended it to their number | `server.js:2078-2080` |

And `placeCallback` — the one place a call-back is ever dialled — names that
list as its absolute gate:

```js
// server.js:337,340-341
// 2. Do-not-call is absolute.
const dnc = suppress.isPhoneSuppressed(rec.accountId, to);
if (dnc.blocked) { ...; return { ok: false, reason: 'That number asked not to be contacted.' }; }
```

It is absolute only for as long as the row survives.

### 1c. Nothing else records the opt-out, so there is no second line of defence

This is the part that makes it High rather than Low. `callbackAllowed`'s very
first gate looks like a second line of defence:

```js
// lib/callback.js:66
if (rec.optedOut) return { ok: false, reason: 'They asked us not to call.' };
```

**`optedOut` is never written by anything.** `grep -rn optedOut server.js lib/*.js`
returns that one line and nothing else. It is a read with no writer — dead code
that reads like a guard. When a caller texts STOP, their consent record is left
completely untouched: `consent` stays `true`, the consent wording and timestamp
stay in place (and are write-once, `lib/db.js:538-547`, so they could not be
amended even if something tried), and `callbackAllowed` keeps returning
`{ ok: true, basis: 'they asked on the web form and ticked the consent box' }`.

From the reproduction, after a STOP:

```
suppression list blocks her:  true
her consent row records it:   optedOut = undefined
consent on the row is still:  true
callbackAllowed on her row:   {"ok":true,"basis":"they asked on the web form …"}
```

So the full chain is four clicks, no attacker, no crafted request:

1. Dana fills a shop's `/f/<slug>` form and ticks the consent box. The AI calls her.
2. Dana texts STOP. Her number is suppressed; her consent record is not changed.
3. The owner sees `12136822616@phone.invalid` · *"They asked to stop"* in the
   Do-not-call list with an **Unblock** button beside it (`views/app.html:1708`)
   and clicks it. The confirm reads **"Unblock …? They can be emailed again."**
   (`views/app.html:1718`) — it does not mention calls at all, on a row that is
   a phone number.
4. The owner clicks **Call back** on her original enquiry. `/api/callbacks/call`
   runs `placeCallback(rec, { by: 'owner' })`, which skips the once-a-day rule
   (`server.js:343`) and quiet hours (`server.js:354`) because `by === 'owner'`.

Reproduction output for step 4:

```
gate 1  consent          -> PASS
gate 2  "DNC is absolute"-> PASS
gate 3  once per day     -> skipped entirely when by === "owner"
gate 5  quiet hours      -> skipped entirely when by === "owner"

RESULT: AI voice call placed to a person who texted STOP: YES
```

And per 2026-11-11 §4, form consent carries no age limit, so her day-1 tick is
treated as live consent however long ago it was.

The exposure is the one `lib/callback.js`'s header is written to avoid: an AI
voice is an "artificial or prerecorded voice" under the TCPA per the FCC's
February 2024 ruling, calling someone who has revoked consent is strict
liability at $500–$1,500 per call, and Dawnpipe owns the Twilio account, writes
the words and runs the dial loop. One suit could also suspend the Twilio
account and take every tenant's inbound line down with it — which is the exact
reasoning `server.js:2883-2896` gives for keeping outbound cold calling off.

### 1d. Why I did not fix it

Removing the Unblock button is not obviously correct. There is a legitimate
case for it: CAN-SPAM lets you mail an opt-out again after they give fresh
affirmative consent, and a shop whose customer rings up and says *"no, do text
me"* has a real need. The product has no way to record that fresh consent, so
the honest fix is a product decision, not a null check. Three questions, with
what I would do:

1. **Should an `unsubscribe`-reason row be removable at all?** I would say no
   for phone rows and yes for email rows with a recorded basis — the asymmetry
   is justified because the phone side is strict-liability and the email side
   is not. At minimum, `reason: 'bounce'` and `'manual'` should stay freely
   removable; they carry no legal weight.
2. **If it stays, what evidence is recorded?** Today: nothing. Not who
   unblocked, not when, not why. The suppression row is deleted outright
   (`db.removeSuppression`, `lib/db.js`), so after the click there is no trace
   that the person ever opted out — which is also the record you would need in
   a dispute. A tombstone (`removedAt`, `removedBy`, `removedReason`) instead
   of a delete would cost one field and keep the evidence.
3. **Either way, `optedOut` should get a writer**, or be deleted. A STOP should
   stamp the consent records for that `phoneKey`, so revocation lives with the
   consent it revokes rather than only in a list that one click clears. That is
   the second line of defence the gate at `lib/callback.js:66` is already
   written for.

The cheapest thing that helps this week, and the only part I would call
unambiguous: **fix the confirm text** (`views/app.html:1718`). "They can be
emailed again" on a `@phone.invalid` row is simply wrong, and an owner clicking
through it has not been told what they are authorising. That is a one-line UI
change, but it is in `views/`, it is the Keeper's half of the house, and it
does not fix the hole — so it goes in §7 rather than on a branch from me.

## 2. The one field on `/api/callbacks/call` with no coercion was the legal timestamp — FIXED

**`server.js:3186`** · severity **Medium** · confidence **high, reproduced
through the route** · branch **`audit/2026-11-18-validate-callback-leftat`**

This is the item last week's report nominated: *"nobody has audited its input
handling or what an owner-supplied `leftAt`/`basis` can write into the consent
evidence."* `basis` turned out to be fine — `String(f.basis || '…').slice(0, 300)`.
`leftAt` was not:

```js
// server.js:3186 — before
consent: true, consentAt: f.leftAt || db.nowISO(), consentText: String(f.basis || '…').slice(0, 300), consentVia: 'owner'
//                        ^^^^^^^^^ no String(), no slice(), no date check
```

Every neighbour in that same object literal is `String()`-ed and sliced —
`name` at 80, `need` at 400, `basis` at 300. This one was taken raw. It then
becomes `consentAt`, which is both the TCPA evidence timestamp and the value
the 90-day age limit is measured against:

```js
// lib/callback.js:85-86
const ageDays = (Date.now() - Date.parse(rec.consentAt || rec.at || 0)) / 86400000;
if (!(ageDays <= 90)) return { ok: false, reason: 'Their enquiry is more than 90 days old — too old to call back on.' };
```

Three things followed. Measured, with the handler's own write:

```
(a) no leftAt (what the app sends)  consentAt "2026-11-18T12:42:05.263Z"  ageDays 0     -> ALLOWED
(b) "last Tuesday"                  consentAt "last Tuesday"              ageDays NaN   -> blocked: "more than 90 days old"
(c) now + 400 days                  consentAt "2027-12-23T12:42:05.264Z"  ageDays -400  -> ALLOWED
(d) 1.5MB of 'A'                    consentAt "AAAAAAAA…"                 ageDays NaN   -> blocked: "more than 90 days old"

callbacks.json is now 1.43 MB
```

- **(b) and (d) fail closed, but with a false reason.** `!(NaN <= 90)` is
  `true`, so the gate refuses — good — and tells the owner the enquiry is *more
  than 90 days old* about a record created a second earlier. A date the owner
  typed in any human form gets this.
- **(c) is the one that matters.** A future timestamp makes `ageDays` negative,
  `ageDays <= 90` holds for ever, and the 90-day limit never expires. The
  record stays dialable indefinitely.
- **(d) writes into the never-pruned store.** `lib/db.js:30-35` calls
  `callbacks.json` *"unaltered, append-only, never pruned"*, and it is
  rewritten in full on every insert. This is the same amplifier as the standing
  CRITICAL — bounded by `MAX_BODY` at 2MB per request — but behind a session
  and a paid plan, which is why this is Medium and that one is critical.

**Honest scope:** the app's own UI never sends `leftAt` (`views/app.html:1428`
sends `{name, phone, need, basis}`), so this is reachable only by a crafted
request from an authenticated paying customer. It is a latent correctness bug
in the request contract, not a live incident.

### The fix

Parse it, clamp it to now (nobody left their number tomorrow), fall back to now
when it is not a date:

```js
const leftMs = Date.parse(String(f.leftAt || ''));
const leftAt = Number.isNaN(leftMs) ? db.nowISO() : new Date(Math.min(leftMs, Date.now())).toISOString();
```

`test-callbackconsent.js` added: 14 assertions over real HTTP POSTs to the
route. **8 fail on `main`**, 0 fail with the fix. All six existing suites still
pass. `node --check` clean on `server.js` and every file in `lib/`. The branch
also merges cleanly on top of the Keeper's bundle, and the call-back suites in
that bundle still pass with it applied — so the two can be taken in either
order.

## 3. The free-autofill grant is spent before any work is done — Low

**`server.js:2457-2459`** · confidence **high, from the code** · not fixed
(reported, it is one line but it sits in a gate with a pending branch on it)

```js
const freeAutofill = p === '/api/profile/autofill' && !stripe.hasAccess(account)
  && Number(account.autofillsUsed || 0) < 2;
if (freeAutofill) db.updateAccount(account.id, { autofillsUsed: Number(account.autofillsUsed || 0) + 1 });
```

The counter is incremented **in the paywall gate**, which runs before method
dispatch and before the autofill is attempted. So a locked account spends one
of its two free demo autofills on:

- **a GET** to `/api/profile/autofill` — the handler is POST-only
  (`server.js:2526`), so the request falls through the whole `/api/` block and
  does no work at all; and
- **any POST that then throws** — and `autofillFromWebsite` throws readily:
  *"Enter your website URL"*, *"That doesn't look like a valid URL"*,
  *"Couldn't read that site…"* (`lib/agents.js:120,123,149`).

The grant exists for a specific moment, and the comment says so: *"A locked
account gets 2 free website-autofills so the in-person demo ('watch it read
YOUR site') works before any card."* Two fumbles at the URL in front of a
prospect — a typo, then a site behind a WAF — and the demo is over with nothing
shown. That is a sales bug, in the gate whose comment is about a sale.

**Note on the pending branch:** `keeper/2026-10-10-mutate-account-autofill`
fixes the *lost-update race* on this counter (09-23 §6) by moving it into an
atomic `db.mutateAccount`. I checked its diff. It does not change *where* the
increment happens, so it does not address this; both are still true after it
merges. The fix is to move the increment to the success path, which means the
gate has to grant permission without consuming it — slightly more than a
one-liner, which is why it is reported rather than pushed.

## 4. Checked and sound

Gone through under this lens and found correct, so a future run need not
re-derive them. (10-28 cleared `/webhook/stripe`, `reconcileCheckout`, tenant
scoping, `updateCallback`'s consent lock, `/f/<slug>`, `/partners/apply`,
`hooks.emit`, the night-shift scheduler, `/api/admin/reps/pay` and
`/api/voice/numbers/release|reassign`; I did not re-audit those, except where
noted.)

- **`/sms/incoming`** (`server.js:1112-1195`) — the big one this run, and
  unopened by any previous report. Signature-verified identically to the voice
  webhooks before anything else runs; STOP/START handled before the model, as
  law rather than preference; `account.voice` is the **per-profile** resolved
  config (`server.js:1127`), so the `callBackMissed` gate at `:1150` reads the
  business that owns the line rather than the account default — consistent with
  what `/api/callbacks/settings` writes. The YES-consent capture is sound: the
  `offered` row carries no `consentAt` (`server.js:1989-1990`), so
  `updateCallback`'s write-once lock does not strip the consent fields on the
  way in, which is what I went looking for — a pre-stamped `consentAt` there
  would have silently broken the whole missed-call call-back feature. A second
  YES finds no `offered` row and falls through to the agent. Thread turns are
  capped at 40 (`lib/db.js:saveThread`), so the prompt cannot grow without
  bound.
- **The 1.5-second window on the SMS YES path** (`server.js:1158`). The row is
  set to `status: 'queued'` with no `dueAt` and then dialled by a `setTimeout`
  1500ms later, so for that 1.5s it is also visible to the 60-second
  `runCallbackQueue` tick. I chased this as a double-dial and it does not
  reproduce: the tick re-reads the row and skips it unless it is still
  `queued`, and if the tick wins, `placeCallback`'s `calledToday` check closes
  on the `setTimeout`'s stale snapshot because `by` defaults to `'system'`
  there, not `'owner'`. The `/f/<slug>` form path has no window at all —
  `addCallback` defaults to `status: 'new'` (`lib/db.js`), which the queue
  filter does not match.
- **Twilio signature verification** (`server.js:1119,1209`; `lib/voice.js:156-163`).
  Length-checked before `timingSafeEqual`, so no throw on a short header, and
  reconstructing the URL from `x-forwarded-*` is not a bypass — a forger still
  needs the auth token. I specifically checked that the signed URL drops the
  query string (`base + p`, where `p` is `url.pathname`): every webhook URL the
  code hands Twilio is query-free (`lib/numbers.js:68-93`, and the fourteen
  `base + '/voice/…'` action URLs), so nothing is being verified against the
  wrong string.
- **`/partners/apply` header injection** (`server.js:2158-2175` →
  `lib/smtp.js:149`). I re-checked this one despite 10-28 clearing the handler,
  because the subject is `Partner application: ${name}` with `name` from an
  unauthenticated JSON body, capped but not CR/LF-stripped. It is safe:
  `encodeHeader` base64-wraps anything outside `[\x20-\x7E]`, and CR and LF are
  outside it, so a line break forces RFC-2047 encoding rather than a new
  header. `lib/smtp.js:93` documents exactly that reasoning and the code
  matches it.
- **`/api/suppression/add`** (`server.js:3348-3362`). Splits on all plausible
  separators, routes `@` to email and ≥10 digits to phone, and refuses an empty
  request. The complement of §1 and correct.
- **`/health`** (`server.js:905-915`). First thing in the handler, depends on
  nothing that can throw, and leaks configured-or-not flags only, never
  credentials.
- **`/checkout` and `/billing`** (`server.js:2363-2392`). Both sit after the
  auth gate at `:2355`, so `account` cannot be null. The portal-failure branch
  deliberately does not fall through to Checkout, with the double-charge it
  would cause spelled out in the comment.
- **`/api/leads/import`** (`server.js:3570-3587`). Row count is clamped to the
  plan's remaining allowance with a hard 5000 ceiling. Worth knowing for a
  future (b) run, not a finding here: `f.rows` is spread into the store with no
  field whitelist, and import does not itself consume quota, so the clamp
  bounds each request rather than the total. AI cost stays bounded because
  drafting is what meters.
