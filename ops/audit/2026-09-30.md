## Headline 2 — an unreadable store file is silently emptied, then overwritten for good

**New this run. Fix implemented, tested and pushed — not merged, so production is
exposed.** Branch: `audit/2026-09-30-preserve-unreadable-store-files`.

I checked every other open branch for a duplicate; none touches `read()`.

`main:lib/db.js:43`:

```js
function read(f, fb) { try { return JSON.parse(fs.readFileSync(f, 'utf8')); } catch { return fb; } }
```

This returns the empty fallback for *any* failure, so "this file will not parse"
and "there are no records yet" are indistinguishable. Nothing throws, nothing is
logged, the app keeps serving — and then the next ordinary write persists that
emptiness over the real records. There are no backups anywhere in the repo, so
the loss is total and permanent.

**Failure scenario**, reproduced end to end against the real `db.js`:

1. `accounts.json` becomes unreadable — zero length or truncated.
2. `getAccountByEmail()` returns `null` for everyone; every login fails.
3. One public signup calls `createAccount()`, which reads `[]`, pushes one
   account, and writes. **Every other customer is now gone from disk.**

Measured on unpatched `main`, three accounts and two calls seeded:

```
before:  accounts = 3   calls = 2
after zero-length file:  allAccounts() -> 0   (no throw, no log, silently empty)
after ONE ordinary write on each path:
  accounts.json now holds 1 account(s)     <- a single signup
  calls.json   now holds 1 call(s)         <- a single live voice webhook
  a@x.com recoverable? -> null
```

`calls.json` goes the same way via `saveCall()` on any live call, which also
destroys the `accountByCallSid()` fallback that bills minutes when a deploy lands
mid-call.

**What triggers the corruption.** `write()` (`main:lib/db.js:44`) does
`writeFileSync(tmp)` then `renameSync(tmp, f)` with **no `fsync` on the file or
the directory**. That survives a clean restart, but on an unclean kill ext4's
delayed allocation can publish the renamed file at zero length — the classic
rename-without-fsync outcome. An unclean kill is not hypothetical: Render Starter
is a 512 MB instance and finding 3 shows every voice turn parsing and
re-serialising a multi-megabyte file, which is the allocation churn that earns an
OOM `SIGKILL`. A full 1 GB disk (finding 4) is a second path.

**Confidence: high** that the amplification is real — reproduced above, on quoted
code. **Moderate** on how often the triggering corruption happens: it needs an
unclean kill or a full disk, neither of which is known to have occurred. The
honest framing is not "this is happening" but "if it happens once, the customer
list is gone and nothing warns you".

**The fix** separates the two failures the original conflated:

- A failure to **read** (absent on cold start, `EMFILE`, `EIO`, `EACCES`) says
  nothing about the contents, so the file is left strictly alone. This matters —
  quarantining on a transient blip would itself destroy a healthy store.
- Only unparseable **content** is quarantined: renamed to `<file>.corrupt-<ts>`
  and logged loudly, so the next write recreates the file and the app stays up
  while the original bytes remain on disk to restore by hand.

Verified: cold start and the happy path create no quarantine file; a truncated
`accounts.json` is preserved byte-for-byte with its surviving records readable,
where before it was overwritten; quarantine fires once, not on every read.
`node --check` clean, all 58 exports intact.

This is damage *containment*, not prevention. Prevention needs fsync and backups
— both judgement calls, see "Not implemented".

## 3. The flat store's real limit under concurrent calls is a blocked event loop, not lost writes

This answers COST.md's open question, and it is not what COST.md and AUDIT.md
assume.

**Lost writes are not the failure mode.** Node is single-threaded and every
`db.js` function is a fully synchronous read-modify-write, so two webhooks cannot
interleave inside one. A lost update needs a snapshot, an `await`, then a write
derived from that stale snapshot — and the counter paths already guard against
exactly that:

- `server.js:1876` re-reads with `db.getAccount(call.accountId)` on the line
  immediately before `consumeVoiceMinutes` — no `await` between them.
- `server.js:1858-1862`, the deploy-mid-call billing fallback — same, synchronous.
- `server.js:568` re-reads `sentToday` mid-run, with a comment explaining why.
- `lib/agents.js:471` re-reads per iteration, with a comment explaining why.

That last one is the 2026-09-02 finding's fix, and it is *already on `main`* even
though `audit/2026-09-02-consume-stale-snapshot` is unmerged — so it was applied
by some other route. Worth knowing before anyone tries to merge that branch.

**Voice-minute billing is free of lost updates and of double-billing.** I went
looking for both and did not find them. Recording it as a clean result on a
revenue-critical path. (`keeper/2026-09-13-topup-write-race` concerns Stripe
top-up crediting in `lib/stripe.js`, a different path, and is unmerged.)

**What does break is latency.** Every operation reads, parses, re-serialises and
rewrites the *entire* collection, blocking the event loop for every other call in
flight. `server.js:1583` calls `saveCall` on **every conversational turn**, and
`logActivity` is called from ~100 sites in `server.js`.

Measured against the real `db.js` with realistic records (~180 chars/turn, per
COST.md), on this dev box:

```
calls.json   at its own 3000-record cap    6.5 MB  -> saveCall     39 ms  (max 111)
activity.json  10 accounts x 500 rows      0.9 MB  -> logActivity  10 ms
activity.json  50 accounts x 500 rows      4.7 MB  -> logActivity  83 ms
activity.json 200 accounts x 500 rows     19.0 MB  -> logActivity 396 ms
```

500 rows/account is the cap `capPerAccount` itself allows and 200 customers is
COST.md's planning horizon — so **~435 ms of fully blocked event loop per voice
turn at the target scale**, before Render's shared CPU makes it worse. At 4
turns/min/call that saturates one instance near **30 simultaneous calls**, and
the ceiling is single-threaded blocking I/O, so more CPU does not move it. Past
saturation webhooks queue until Twilio times out, which on a live call is dead
air for a real customer of a real plumber.

`keeper/2026-09-02-db-write-compact` (unmerged) drops the pretty-printing and
helps: 396 ms → 316 ms at 200 accounts. That measurement understates its benefit,
because my seed files stayed pretty-printed so only the write side got cheaper.
It does not change the order of magnitude. `keeper/2026-09-05-per-account-retention`
(unmerged) caps `calls`/`smsThreads` per account, which bounds those two files
but not `activity` or `sendlog`.

**Confidence: high** on the measurements and mechanism; the 30-call figure is an
order-of-magnitude estimate, not a promise.

Not implemented — reducing whole-collection rewrites on the hot path is an
architecture change, which this brief says to describe rather than ship.

## 4. `sendlog.json` is uncapped, holds full message bodies, and is rewritten whole on every send

`main:lib/db.js:176`. `logSend` is deliberately append-only ("never edited" — it
is the evidence trail), but nothing caps or rotates it and it stores the complete
body of every message. Every send re-serialises the entire history:

```
  5k sends    7 MB  -> logSend    39 ms
 25k sends   37 MB  -> logSend   840 ms
100k sends  147 MB  -> logSend  3231 ms
```

At 200 customers × 200 leads/mo that is ~40k sends/month: past a second of
blocking per send within a couple of months, heading for the **1 GB Render disk**
— which, once full, is a direct trigger for Headline 2. `callbacks.json` (TCPA
evidence) and `appointments.json` are also uncapped but small per row; `sendlog`
is the one with bodies in it.

**Confidence: high** on growth and measurements. Not implemented because "how
long must send evidence stay queryable in-app" is a product decision. Rotating to
dated files (`sendlog-YYYY-MM.json`) bounds the hot file while preserving the
append-only property the comment cares about.

## 5. `findConflict` measures existing appointments with the *proposed* booking's length — a real double-booking

`main:lib/db.js:336-346`:

```js
const len = Math.max(15, Number(slotMinutes) || 60) * 60000;   // the PROPOSED length
...
const e = s + len;    // ...applied to the EXISTING appointment
```

Callers pass `account.voice.slotMinutes` (`server.js:1125` SMS, `server.js:1660`
voice), so every appointment shares one length — until the shop changes that
setting, at which point existing bookings are silently re-measured at the new
length.

**Failure scenario:** a shop with `slotMinutes: 120` books a job at 14:00 (really
occupying 14:00–16:00). They later change the setting to 30. A caller asks for
15:00. `findConflict` computes the 14:00 job's end as `14:00 + 30min = 14:30`,
finds no overlap, and books it. **The plumber is double-booked inside a job that
is still running** — the exact failure `server.js:1655` calls "the failure that
gets us switched off".

**Confidence: high** that the logic is wrong; **moderate** on frequency, since it
needs a settings change after bookings exist.

Not implemented: the minimal fix persists new state and raises a product question
this audit should not settle alone — **should changing the default job length
retroactively change already-booked jobs?** Assuming no, the fix is small: stamp
`slotMinutes` onto the row in `addAppointment`, then in `findConflict` use
`const e = s + (Number(a.slotMinutes) || len) * 60000`, which falls back to
today's behaviour for existing rows.

## Checked and clean

Recorded so a later run need not redo them:

- **No lost updates on any counter path** — voice minutes, leads, `sentToday` all
  re-read before writing (finding 3).
- **No double-billing of voice minutes.** `/voice/status` bills once, excludes
  calls where nobody spoke and calls flagged spam (`server.js:1874-1877`), and
  the deploy-mid-call fallback (`server.js:1858`) only fires when the in-memory
  call is already gone, so the two paths cannot both bill.
- **No TOCTOU in booking.** `findConflict` → `addAppointment`
  (`server.js:1660-1676`) is synchronous with no `await` between, so two
  simultaneous callers cannot race into the same slot. (Finding 5 is a separate,
  non-concurrency defect.)
- **Single instance.** No `cluster`, no `worker_threads`, one Render web service,
  so no cross-process writer races on the shared `.tmp` name in `write()`.
  **`write()` is not multi-process safe** — re-check before ever scaling out.
  (`keeper/2026-09-04-unique-tmp-write`, unmerged, gives it a unique temp name.)
- **Write failures do not corrupt.** If `writeFileSync(tmp)` throws on a full
  disk, `renameSync` never runs and the live file is untouched.

## Not implemented, deliberately

- **fsync before rename** — the real prevention for Headline 2, but an `fsync`
  per voice turn on a 6.5 MB file makes finding 3 materially worse. Doing it well
  means fixing the hot-path writes first, so it is an architecture decision.
- **Backups** — there are none, anywhere. A nightly copy of `data/*.json` to
  object storage is the highest value per hour on this list. Infrastructure, not
  a code change.
- Findings 3, 4 and 5, for the reasons given with each.
