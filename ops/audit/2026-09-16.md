## Finding 1 — SMTP command and header injection via an unvalidated lead address

**Severity: Critical · Confidence: high (reproduced against the real client)**

### The chain

Nothing between "a row in a CSV" and "bytes on a TLS socket" looks at the shape of an
email address.

| Step | Where | What it does |
|---|---|---|
| 1 | `server.js:3483` | `/api/leads/import` stamps every row `emailConfidence: 'imported'` |
| 2 | `lib/db.js:418` | `addLeads()` stores `email: (r.email \|\| '').trim()` — no format check of any kind |
| 3 | `lib/db.js:434` | `'imported'` is in `SENDABLE`, so `isSendableLead()` passes it |
| 4 | `lib/agents.js:485` | the drafter copies it verbatim: `to: lead.email` |
| 5 | `lib/smtp.js:105` | `RCPT TO:<${msg.to}>` |
| 6 | `lib/smtp.js:113` | `To: <${msg.to}>` |

Steps 5 and 6 are line-oriented protocol. `talk()` writes `cmd + '\r\n'` straight to the
socket (`lib/smtp.js:46`), so a CR/LF inside the address is not data — it is the end of
one command and the start of another.

### Reproduction

Stubbed the TLS socket, called the real `sendMail()` with
`to = 'victim@example.com>\r\nRCPT TO:<attacker-target@example.net'`, and printed the wire:

```
[4] "MAIL FROM:<system@dawnpipe.com>\r\n"
[5] "RCPT TO:<victim@example.com>\r\nRCPT TO:<attacker-target@example.net>\r\n"
[6] "DATA\r\n"
[7] "From: Dawnpipe <system@dawnpipe.com>\r\nTo: <victim@example.com>\r\n
     RCPT TO:<attacker-target@example.net>\r\nSubject: hi\r\n..."
```

One lead row, two `RCPT TO` commands. The same bytes in the header block (`[7]`) can carry
`\r\n.\r\n` and close `DATA` early, which starts a fresh `MAIL FROM` transaction — arbitrary
sender, arbitrary recipients, arbitrary body. `dotStuff()` protects the body only; the
header block is joined unprotected.

### Why it is Critical rather than "they're abusing their own mailbox"

`server.js:14-21` — an account with `smtp.useDawnpipe` sends through `mailer.systemCfg()`,
**our** system mailbox. `/api/settings/smtp` sets that mode with one click and no
credentials. So the injected recipients and forged headers leave Dawnpipe's own sending
domain, and the complaints and blocklist entries land on it.

COST.md names this exact asset: *"every customer connects their own mailbox, so Dawnpipe
pays for no sending infrastructure and carries no sender-reputation risk on its own
domains. That is a real structural advantage over any competitor running a pooled ESP."*
One abusive account spends that advantage permanently, and there is no throttle or content
check on the shared-mailbox path that would notice.

The subject line was never exposed: `encodeHeader()` (`lib/smtp.js:78`) base64-wraps
anything outside printable ASCII, and CR/LF are outside it. That cover is accidental but
real, and it is why only the envelope fields are affected.

**Preconditions, stated plainly:** an account that has reached `hasAccess` (a 7-day trial
counts — `/api/send/run` is gated on access, not on payment) and, for the worst version,
`mailer.enabled()` plus the one-click "let Dawnpipe send for you". Not anonymous. Cheap.

### Fixed — `audit/2026-09-16-smtp-crlf-injection`

Rejects CR/LF in the values that reach a command or a header line with no other cover: the
recipient, the envelope sender, the attachment name and type, and the unsubscribe URL.
Subject and sender name deliberately untouched (`encodeHeader` already covers them; a guard
there could only invent a new failure).

One detail worth keeping: the thrown message is fed to `suppression.isHardBounce()` by the
send loop (`server.js:577`), whose pattern list includes `invalid recipient` and `address
rejected`. A guard worded the obvious way would have permanently suppressed the address as
though the mailbox were dead. The wording avoids every trigger; verified `isHardBounce()`
returns `false` on it.

Verified: injection refused before a socket opens · ordinary sends, RFC 2047 unicode
subjects and the attachment path byte-for-byte unchanged · `node --check` clean ·
`test-sending-mode.js` 9/9 and `test-spam.js` 18/18 still pass.

**Still worth doing beyond the patch (not implemented — product call):** validate the
address at `db.addLeads()` so a malformed row is rejected at the door rather than at the
socket, and consider whether the shared system mailbox should carry a per-account
reputation budget at all.

## Finding 2 — SSRF: `/api/profile/autofill` fetches any URL the caller names

**Severity: Medium-High · Confidence: high on the code path (reproduced), unverified on
what is actually reachable from Render**

`lib/agents.js:118-142`. The onboarding "paste your website" flow takes a caller-supplied
URL, prefixes `https://` only if no scheme is present (`:121` — so an explicit `http://`
survives), and fetches it plus `/about`, `/about-us` and `/services` with
`redirect: 'follow'` (`:104`). There is no host, scheme or IP-range check anywhere on the
path, and the content-type gate `/text|html/i` (`:108`) admits `text/plain`.

The fetched text is then handed to the model and the drafted fields are returned to the
caller (`server.js:2427-2428`), so this is not blind — internal content comes back
summarised.

Reproduced by stubbing `globalThis.fetch` and calling the real `autofillFromWebsite`:

```
URLs fetched server-side:
   http://169.254.169.254/latest/meta-data/iam/security-credentials/
   http://169.254.169.254/about
   http://169.254.169.254/about-us
   http://169.254.169.254/services
returned to the caller: {"name":"Internal","offer":"leaked text"}
```

**Reachable by an unpaid account.** `server.js:2355` grants a locked account two free
autofills so the in-person demo works before a card. Signup is throttled at 20/hour per IP
(`server.js:2162`), so that is 40 arbitrary server-side fetches per IP per hour with no
payment at all, and unlimited for any paying account.

**Not fixed — this needs a decision, not a patch.** Blocking private ranges correctly means
resolving the hostname first, rejecting loopback/link-local/RFC1918/RFC6598 and IPv6
equivalents, re-checking after every redirect, and handling DNS rebinding — which in raw
Node means pinning the resolved address into the connection. That is a real piece of work
and it can break legitimate customer sites if done carelessly. The cheap interim step, if
you want one this week, is to reject non-public literal IPs and `localhost` before the
first fetch and set `redirect: 'manual'`; it stops the casual version without pretending to
be complete.

What is actually reachable from a Render service I could not test — production access this
run was read-only and anonymous, and probing it would have meant exactly the requests this
finding is about. Treat the code defect as confirmed and the blast radius as open.

## Finding 3 — `esc()` does not escape quotes, and is used inside HTML attributes

**Severity: Medium · Confidence: high on the sink, medium on the delivery path**

`views/app.html:1099`:

```js
function esc(s){return (s||'').replace(/[&<>]/g,c=>({'&':'&amp;','<':'&lt;','>':'&gt;'}[c]));}
```

Fine between tags. But ten templates in the same file use it inside a **double-quoted
attribute** — `title=`, `value=`, and several `onclick=`. A value containing a bare `"`
closes the attribute and opens whatever follows.

Most of those are self-XSS (a customer's own leads, their own suppression list). One
crosses an account boundary: `views/app.html:1834`, `loadUnattributed()`, which renders
**other accounts' email addresses** into the owner-only Sales Reps screen:

```js
<button class="sm ghost" onclick="$('as_email').value='${esc(a.email)}';…">
```

`POST /signup` (`server.js:2166-2168`) applies no format check to an address whatsoever —
non-empty and lowercased is the whole test. So `a" onmouseover="…" x="@b.com` is a valid
signup address and becomes a live event handler in the owner's page, needing a hover rather
than a click. That handler runs with the owner's session against every `/api/admin/*` route.

**What I could not confirm:** `/api/admin/reps/unattributed` (`server.js:3172`) filters on
`subStatus` in `active`/`trialing`, which means the address has to survive Stripe Checkout —
`createCheckout` passes it as `customer_email` (`lib/stripe.js:354`) and Stripe does its own
validation. I have no way to test Stripe's validator from here without transacting. The sink
is confirmed; the delivery path is not.

**Partly fixed — `audit/2026-09-16-esc-quotes`.** `esc()` now escapes `"` and `'`, which
closes the no-interaction attribute breakout everywhere at once. All 96 call sites feed
`innerHTML`, so nothing changes visually.

It is **not** a complete fix and the commit says so: in `onclick="fn('${esc(x)}')"` the
parser decodes `&#39;` back to `'` before the JS is parsed, so a quote still terminates that
string literal and a *click* can still run injected code. The real fix is to stop building
handlers by string interpolation — `data-*` attributes plus a delegated listener — which is
a UI refactor, not an audit patch.

## Finding 4 — the Stripe webhook accepts a signature of any age

**Severity: Medium · Confidence: high**

`lib/stripe.js:476-485`. The timestamp is parsed out of the header and folded into the
signed string (`:480`) but **never compared to the clock**. Stripe's own libraries enforce a
300-second tolerance by default, and Dawnpipe's own outbound-webhook verifier does it
correctly one file over — `lib/hooks.js:56-60`, `toleranceSec = 300`. The inbound path is
the one holding money and it is the one that skips the check.

Concretely: any single captured `(body, Stripe-Signature)` pair replays forever. The
idempotency that exists is partial — `creditTopup()` dedupes on session id but keeps only
the last 50 (`lib/stripe.js:441-445`), and `checkout.session.completed` re-applies
`subStatus: 'active'` unconditionally (`:537-541`), so a replayed completion re-activates a
cancelled account.

**Not fixed, deliberately.** The obvious patch is four lines, but a tolerance check on a
live payments path turns any clock skew into a total billing outage, and that is a
risk-appetite decision about production, not an audit call. My recommendation: add it with
a 300s tolerance to match Stripe's own default and `hooks.verify`, and log-but-accept for
one week before enforcing, so skew shows up in the activity log rather than in lost
webhooks. Also worth pairing with event-id idempotency —
`keeper/2026-09-03-billing-idempotency` already exists and has been waiting 13 days.

## Checked and clean

Listing these so a future run knows what it can skip and what it cannot.

- **Twilio signature verification** (`lib/voice.js:156-163`) — correct algorithm, sorted
  params, length check before `timingSafeEqual`, rejects outright when no auth token is
  configured. Applied before any work on both `/voice/*` (`server.js:1155`) and
  `/sms/incoming` (`server.js:1065`). The URL is rebuilt from `x-forwarded-host`, which is
  attacker-controlled, but a forged host does not help without the auth token, and the
  comment explains the domain-migration reason. Fine.
- **Session handling** (`lib/auth.js`) — HMAC-signed cookie over a 24-byte random token that
  *also* indexes a server-side record, so knowing the secret alone forges nothing.
  `timingSafeEqual` with a length guard. `scryptSync` at defaults. HttpOnly, SameSite=Lax,
  Secure when `PUBLIC_URL` is https. I specifically checked `getSession('__proto__')` and
  `getSession('constructor')` for prototype-pollution auth bypass: both dead-end at
  `getAccount(undefined)` → `null`, and neither is reachable past `unsign()` anyway.
- **Unsubscribe tokens** (`lib/suppression.js:31-45`) — HMAC-verified, `timingSafeEqual`,
  length-checked. The unescaped `${parsed.email}` at `server.js:2013` is therefore only
  reachable with a valid MAC, i.e. an address we genuinely mailed. Not a finding.
- **Owner-only routes** — all twelve `/api/admin/*` handlers carry
  `if (!stripe.isOwner(account)) return … 403` on their first line. No gaps.
- **Secret handling in `/api/state`** (`server.js:2369-2400`) — the mailbox password is
  masked to a `connected` boolean and the Hunter key to `connected`. Correct.
- **`/api/voice/recording`** (`server.js:2617`) — the recording SID is looked up inside
  `db.getCalls(acc, …)` before the proxied fetch, so it is account-scoped. No IDOR.
- **Command injection** — the only `child_process` use is `lib/ai.js:100`, dev-only
  (`ALLOW_CLI_FALLBACK=1` with no API key), fixed argv, prompt over stdin. No shell
  interpolation. No dynamic `require`, no `eval`, no user-controlled path joins.
- **TwiML output** — `voice.esc()` escapes `& < > " '` and is applied on every interpolation
  into `<Say>`/`<Message>`.
- **Body-size limit** — `MAX_BODY` 2MB with `req.destroy()` on overflow (`server.js:72-86`),
  applied before parsing on every route.

## Noted, not findings

- **`/api/settings/smtp` is an outbound TLS port scanner.** An authenticated user sets an
  arbitrary `host`/`port` (`server.js:3355`), the server connects, and the raw error comes
  back in the response (`:3383`) — enough to distinguish refused from filtered from
  TLS-speaking. It is inherent to a bring-your-own-mailbox product and the payoff is small,
  but if the SSRF in Finding 2 gets an IP-range check, this is the second place to apply it.
- **User enumeration by timing on `/login`.** `getAccountByEmail` misses return before
  `scryptSync` runs, so a wrong address answers measurably faster than a wrong password.
  Textbook, low value against a 10-per-15-minutes throttle. Mentioning it only so a future
  run does not re-derive it.
- **`SESSION_SECRET` falls back to `'dev-insecure-secret'`** (`lib/auth.js:21`,
  `lib/suppression.js:32`). Not exploitable on its own (see above), but it means a missing
  env var fails silently rather than loudly. A startup assertion would be cheap.
