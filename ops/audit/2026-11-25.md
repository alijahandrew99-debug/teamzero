## 1. One row in the block list silently switches off the entire voice product — FIXED

**`lib/suppression.js:55` (`isSuppressed`), `lib/suppression.js:61-67`
(`suppress`), `lib/suppression.js:95-104` (`phoneKey`),
`server.js:3358`** · severity **Medium** · confidence **high, reproduced end
to end** · branch `audit/2026-11-25-suppress-phone-namespace`

Repro committed at `ops/audit/2026-11-25-repro-suppress-namespace.js`. It runs
in a throwaway `DATA_DIR`, places no calls, sends nothing, and drives the real
modules.

### 1a. Two reasonable decisions that are not reasonable together

Phone numbers deliberately share the email suppression list, so that "stop
calling" and "stop emailing" are one opt-out. The comment says so plainly:

```js
// lib/suppression.js:91-94
// Phone numbers live in the same suppression list as email addresses, keyed as
// <digits>@phone.invalid. One list, one opt-out: someone who says "stop calling"
// on a call is also never emailed, and vice versa.
function phoneKey(number) { ... return `${d}@phone.invalid`; }
```

Separately, `isSuppressed` honours a whole-domain block:

```js
// lib/suppression.js:54-56
const dom = domainOf(e);
const domHit = list.find((s) => s.domain === dom && s.wholeDomain);
if (domHit) return { blocked: true, reason: domHit.reason, at: domHit.at, note: `Whole domain suppressed (${dom})` };
```

Both are right in isolation. Together: `phone.invalid` is not a real email
domain. It is the **same domain for every phone number in every account**. So
a single `wholeDomain` row on it does not block one sender's mail — it matches
`domainOf()` for every number the account will ever check.

### 1b. What breaks

```
  before: +13125550202 blocked = false
  suppress(acc, '13125550202@phone.invalid', 'manual', { wholeDomain: true })
  FAIL  one wholeDomain row does NOT block every other number
        -> unrelated +19998887777 blocked=true note=Whole domain suppressed (phone.invalid)
```

`isPhoneSuppressed` now returns blocked for every number on the account, which
means:

- **`server.js:1230`** — `/voice/incoming` `<Reject>`s every inbound call
  before it is answered. The caller hears a busy/rejected tone.
- **`server.js:1139`** — `/sms/incoming` drops every text with an empty
  `<Response/>`.
- **`server.js:2770`, `server.js:2975-2976`, `server.js:340`** — every dial
  path refuses: the test call, the bulk dialler, and `placeCallback`.

That is the whole $399/mo Front Desk product, off. And the symptom points
nowhere near the cause: there is no error, no log line, no activity entry —
calls simply stop arriving. The suppression UI shows the cause as a single
ordinary-looking address row with a "whole domain" pill
(`views/app.html:1706`).

### 1c. How it is reached — and the honest limit on this finding

`/api/suppression/add` forwards `wholeDomain` straight from the request body
and applies it to **every** address in the batch:

```js
// server.js:3357-3358
const emails = parts.filter((e) => e.includes('@'));
for (const e of emails) suppress.suppress(acc, e, 'manual', { wholeDomain: !!f.wholeDomain });
```

Anything containing `@` is classed as an email address, so both
`13125550202@phone.invalid` and the bare `@phone.invalid` get through
(`domainOf` resolves both to `phone.invalid`).

**The shipped UI never sends `wholeDomain`** — `views/app.html:1714` posts
`{emails}` only. So this is reachable by a hand-written API call against the
owner's own account, not by a click. It is a footgun with a whole-product blast
radius rather than an exploit, and I am rating it Medium on that basis, not
High. Two things still make it worth fixing rather than noting:

1. The copy-paste path is plausible. `/api/suppression` returns raw rows and
   the UI renders phone suppressions literally as `13125550202@phone.invalid`.
   An owner cleaning up their block list by API, or a customer's own
   integration doing it, is pasting exactly the string that triggers this.
2. `tz_session` is `SameSite=Lax` (`lib/auth.js:58`), so a cross-site POST
   carries no cookie and CSRF is not an amplifier here. I checked that
   specifically because it would have raised the severity. It does not.

### 1d. The fix

Guarded at **both** boundaries, which matters more than it looks:

- `suppress()` refuses to write `wholeDomain` when the domain resolves to
  `phone.invalid`, so no new row can be created.
- `isSuppressed()` does not consult the whole-domain rule for that domain at
  all, so **a row the old code already wrote stops taking the account's phones
  down the moment this deploys.** A write-boundary guard alone would leave an
  already-poisoned `suppression.json` broken after upgrade, with no way to see
  why. The repro covers that case explicitly (`a pre-existing bad row no
  longer blocks every number`).

A `wholeDomain` block on a real domain is untouched; four assertions pin that.

## 2. `/login` is an unauthenticated CPU amplifier that stalls the voice product — NOT fixed

**`server.js:2298-2305`, `lib/auth.js:12-17`, `server.js:134-137`** ·
severity **High** · confidence **high, measured** · **not fixed — needs an
architecture decision, see §2d**

This is a new conclusion built from two facts that were already in these
reports separately, plus a measurement that had not been taken.

### 2a. The two known halves

**Known half one** (10-14, and 11-04 reproduced it): `rateLimited` keys on the
**leftmost** `X-Forwarded-For` entry with no trusted-hop count, so every rate
limit in the app is bypassed by varying one header.

```js
// server.js:135-136
const ip = (req.headers['x-forwarded-for'] || '').split(',')[0].trim()
  || req.socket.remoteAddress || 'unknown';
```

Still unfixed on `main`. 11-04 measured `25/25 POSTs accepted past a 20/hour
throttle`.

**Known half two** (09-16, in passing, under "things that are fine"):
`scryptSync` at defaults, and `getAccountByEmail` misses return before it runs.

```js
// server.js:2302-2303
const acc = db.getAccountByEmail((f.email || '').trim().toLowerCase());
if (!acc || !auth.verifyPassword(f.password || '', acc.salt, acc.passHash)) {
```

`verifyPassword` is `crypto.scryptSync` (`lib/auth.js:13`) — **synchronous**,
so it blocks the event loop for its whole duration. Node is single-process
here; there is no cluster, and Render runs one instance.

### 2b. What nobody had measured

Put the two together and `/login` becomes an unthrottled, unauthenticated way
to buy ~30ms of un-yieldable CPU per HTTP request. Measured against the real
server with signed Twilio webhooks:

```
  idle: Twilio webhook median 1ms, max 4ms
  single /login, existing email  : 34ms (status 401)   <- scryptSync runs
  single /login, unknown email   :  1ms (status 401)   <- short-circuits, no scrypt
  flooding 60 concurrent /login (fresh X-Forwarded-For each) ...
  during flood: Twilio webhook latencies [77,69,59,55,57,55]ms
  flood finished in 1785ms; 429s returned: 0/60
```

**Sixty requests from one source, zero rate limited, and the voice webhook
path got 55–77x slower.** 60 requests is nothing; the ceiling is wherever the
attacker's bandwidth is. At ~33 req/s the event loop is 100% occupied in
scrypt and Dawnpipe answers nothing at all.

The reason this is a *security* finding and not a capacity note is what is on
the other side of that event loop. A stalled process does not drop a page view
— it misses the `<Gather>` window on a live call. The caller hears silence, the
agent never speaks, and `/voice/status` arrives late or not at all, which is
the same input the stuck-call sweeps exist to clean up. Voice is ~95% of cost
of goods and the entire product promise (COST.md); this is the cheapest known
way to turn it off from outside.

### 2c. Two things I am NOT claiming

**The user-enumeration oracle is not new.** The 34ms-vs-1ms gap tells an
attacker whether an address has an account, which is exactly the fact
`/forgot` goes out of its way to hide (*"Always the same answer — never reveal
whether an email is registered"*, `server.js:2235`). **09-16 already recorded
this**, under "User enumeration by timing on `/login`". I am not re-claiming
it; I am pointing out that it is the *prerequisite* for §2b — you need one
valid customer email, and `/login` hands it to you.

**The `===` on the API key is not worth a finding.** Last week nominated
`db.allAccounts().find((a) => a.apiKey === bearer)` (`server.js:2331`) as a
non-constant-time comparison. I looked and I am going to disagree: a remote
timing attack on a V8 string comparison, through HTTP, a proxy and the event
loop, against a 192-bit random key, is not a realistic trigger. Reporting it
would be exactly the hypothetical this audit is told not to manufacture. The
32-byte `timingSafeEqual` in `lib/auth.js:30` and
`lib/suppression.js:42` are correct and should stay; this one is noise. (It
would still be *tidier* as `timingSafeEqual`, which is a `/simplify` item, not
a security one.)

### 2d. Why I did not fix it

The obvious one-line fixes are each wrong on their own:

- **Equalise the timing** (dummy scrypt on the unknown-email path) closes the
  oracle in §2c and makes §2b strictly **worse** — every request then costs
  30ms instead of only those naming a real customer.
- **Make the rate limit real** (count proxy hops, or key on
  `req.socket.remoteAddress`) needs one production measurement first: what
  Render actually appends to `X-Forwarded-For`. 10-14 and 11-04 both asked for
  that measurement and it still has not been taken. Guessing wrong either
  leaves the bypass open or locks out every customer behind one NAT.
- **`scrypt` async** (`crypto.scrypt`, not `scryptSync`) is the real fix for
  the blocking, and it is a behavioural change to the login path on a live
  revenue product. That is a decision, not a null check.

The right sequence, and it is small: (1) log the raw `X-Forwarded-For` on one
production request — one line, one request, and it unblocks three findings
across three reports; (2) move `verifyPassword` to async `scrypt`; (3) then
equalise the timing, which is free once a request no longer blocks.

## 3. A negative `?limit` on `/v1` removes the 500-row cap entirely — FIXED

**`server.js:2336`, `lib/db.js:223-225` (`getCalls`), `server.js:2338`** ·
severity **Low** · confidence **high, reproduced** · branch
`audit/2026-11-25-v1-limit-clamp`

A different bug from the known one in the same two lines. `/v1/calls` and
`/v1/bookings` share one limit, documented as capped at 500:

```js
// server.js:2336
const lim = Math.min(Number(url.searchParams.get('limit')) || 100, 500);
```

Both reads then end in `.slice(-lim)`. Correct for a positive `lim`; inverted
for a negative one — `.slice(-(-5))` is `.slice(5)`, *"skip the first five
rows"* rather than *"return at most five"* — and the cap is gone. Measured
against a seeded account holding 1,200 calls and 1,200 bookings:

```
  ?limit=500     -> 500 rows    (cap holds)
  ?limit=99999   -> 500 rows    (cap holds)
  ?limit=-1      -> 1,199 rows  <-- cap bypassed
  ?limit=-5      -> 1,195 rows
  ?limit=-500    ->   700 rows
```

Rated Low deliberately: it is the key holder's **own** data, so nothing
crosses a tenant boundary and nothing leaks. What is gone is the only
documented bound on the public API's response size, on a single-process
flat-JSON server. A key is allowed 600 requests an hour (`server.js:2333`);
600 × "read, filter and serialise the entire calls collection" is a cheap way
to make the process spend its hour in `JSON.stringify` instead of answering
Twilio — the same event loop as §2, reached from inside the plan.

Fixed by flooring the clamp at 1 and flooring the number, so a fractional
limit never reaches `slice()` either. Non-numeric and `0` still fall back to
100, exactly as before. 22 assertions; 6 fail on `main`.

**Adjacent and still open, deliberately not in that branch:** `/v1/calls`
applies `since` *after* truncating (09-23 finding 4, re-noted 10-28 and
11-18), so a `since` query can return fewer rows than match it. That wants a
cursor, which is an API-shape decision rather than a clamp.

## 4. A non-string address on the suppression API is a 500 with the internal error in the body — FIXED

**`lib/suppression.js:23` (`norm`), `server.js:3363-3366`,
`server.js:3672`** · severity **Low** · confidence **high, reproduced** ·
same branch as §1

```js
// lib/suppression.js:23 — before
function norm(email) { return (email || '').trim().toLowerCase(); }
```

Every caller reaches `norm` from a JSON request body, where the value can be
anything JSON can express. `/api/suppression/remove` passes it through with no
coercion:

```js
// server.js:3364-3365
const f = parseJSON(await readBody(req));
return json(res, { ok: suppress.unsuppress(acc, f.email) });
```

```
  POST /api/suppression/remove  {"email": 123}     -> 500 {"error":"(email || \"\").trim is not a function"}
  POST /api/suppression/remove  {"email": {"a":1}} -> 500 {"error":"(email || \"\").trim is not a function"}
  POST /api/suppression/remove  {"email": ["a"]}   -> 500 {"error":"(email || \"\").trim is not a function"}
```

Two small things, neither severe. The handler 500s where it should answer
`{ok:false}`; and the outer handler returns `e.message` verbatim to the client
(`server.js:3672`), so an internal expression leaks into the response body.
Authenticated-only, and the message exposes nothing load-bearing — but "the
API returns its own source on a bad type" is the kind of thing that is only
ever reported by someone probing, and it is the same missing-coercion shape as
last week's `audit/2026-11-18-validate-callback-leftat`.

Fixed in `norm()` with `String(email || '')`, which covers `unsuppress`,
`isSuppressed`, `suppress` and `domainOf` in one place. A non-string address
simply is not on the list, so it misses rather than throwing. `null`,
`undefined` and `""` still read as "no address" and still **fail closed** —
three assertions pin that, because turning a fail-closed into a fail-open
would have been a far worse bug than the one being fixed.

### 4a. On the wider `e.message` reflection — checked, not a finding

The non-API branch of the same handler interpolates `e.message` into HTML
unescaped:

```js
// server.js:3688
return html(res, `<pre style="padding:40px;font-family:monospace">${e.message}</pre>`, 500);
```

That is a reflected-XSS shape, so I went looking for a public non-`/api`,
non-`/voice` route that throws with attacker-controlled text in the message. I
did not find one: the paths that parse untrusted input either catch
(`parseJSON`, `parseToken`, `fetchPage`) or sit under `/api/` and answer JSON.
Reporting it as live would be a guess. It is worth escaping anyway as
one-character-cheap defence in depth — queued in §8, not claimed as a finding.

## 5. The collision the nomination asked about — I could not make it happen

Recording a negative result, because "I looked and it is fine" is worth as much
to the next run as a finding, and it stops the same ground being re-walked.

Last week asked whether `norm()`'s lowercasing plus `phoneKey`'s
digit-stripping can collide **two different people** onto one suppression row,
and in particular whether the do-not-call check and the dial could disagree.
That second one is the dangerous shape: `/api/voice/testcall` checks DNC on the
**raw** string and dials a **normalised** one:

```js
// server.js:2769-2775
const dnc = suppress.isPhoneSuppressed(acc, to);     // phoneKey(raw)
if (dnc.blocked) return json(res, { error: ... }, 403);
const call = await voice.placeCall({ to, from, ... }); // placeCall does to = toE164(to)
```

`phoneKey` (`lib/suppression.js:95`) and `toE164` (`lib/voice.js:135`)
normalise *differently* — `toE164` trusts a leading `+` and skips the
10-digit `+1` rule that `phoneKey` always applies. So I checked whether the key
of the input can differ from the key of the number actually dialled:

```
  "3125550202"       phoneKey=13125550202@phone.invalid  toE164=+13125550202  keyOfDialled=13125550202@phone.invalid
  "+13125550202"     phoneKey=13125550202@phone.invalid  toE164=+13125550202  keyOfDialled=13125550202@phone.invalid
  "(312) 555-0202"   phoneKey=13125550202@phone.invalid  toE164=+13125550202  keyOfDialled=13125550202@phone.invalid
  "+3125550202"      phoneKey=13125550202@phone.invalid  toE164=+3125550202   keyOfDialled=13125550202@phone.invalid
  "13125550202"      phoneKey=13125550202@phone.invalid  toE164=+13125550202  keyOfDialled=13125550202@phone.invalid
```

**No mismatch.** The two functions disagree only on `+` followed by exactly ten
digits, and there the divergence **over**-blocks (a 10-digit international
number is checked as though it were US `+1…`) rather than under-blocks. It
lands on unassigned US keys and is self-consistent on the redial, so there is
no DNC bypass and nothing to fix. Not a finding.

The real collision turned out to be one row against *everybody* rather than two
people against each other — §1.

## 7. What this lens confirmed is sound

Worth writing down, because four (c) runs have now covered it and the next one
should start somewhere else.

- **Admin authorization is clean.** All twelve `/api/admin/*` routes carry
  `if (!stripe.isOwner(account)) return json(res, { error: 'Not available.' }, 403)`
  as their first statement, including the money-moving
  `/api/admin/reps/pay` (`server.js:3289`). I checked each one individually.
- **No mass assignment.** All nineteen `db.updateAccount` call sites in
  `server.js` pass explicit field literals. There is no `{...f}` spread
  anywhere near an account patch, so a tenant cannot set their own `tier`,
  `subStatus` or `apiKey` from a request body. This was my strongest
  hypothesis going in and it is simply not there.
- **No prototype-pollution auth bypass.** `db.useResetToken` and
  `db.getSession` both index a `JSON.parse`'d object with a caller-supplied
  key (`lib/db.js:146`, `:119`). `POST /reset` with `token=__proto__` or
  `token=constructor` does reach past the expiry check — `Object.prototype.exp`
  is `undefined` and `undefined < Date.now()` is false — but returns
  `r.accountId === undefined`, and `if (!accountId)` catches it. Verified by
  request, both spellings, 400 and no cookie. `getSession` is unreachable
  without a valid HMAC. No bypass.
- **Webhook signature verification is correct.** Twilio: HMAC-SHA1 over the
  reconstructed URL plus sorted params, `timingSafeEqual` with a length guard,
  `verifySignature` returns **false** when `TWILIO_AUTH_TOKEN` is unset
  (`lib/voice.js:157-158`) — fails closed, which is the one that matters.
  Applied to `/voice/*` (`server.js:1210`) and `/sms/incoming`
  (`server.js:1119`) before any work. The URL is rebuilt from
  `X-Forwarded-Host`, which is attacker-controlled, but controlling the
  *signed string* buys nothing without the token. Stripe signature
  verification is reached before `applyEvent` (`server.js:2320-2323`).
- **`hooks.emit` SSRF stays thin** (10-14's verdict, re-confirmed):
  `https://` only (`lib/hooks.js:36`), the response body never reaches the
  caller, and only an authenticated paying account can configure a URL. The
  status code and error text land in that account's own activity log, which is
  a blind port-scan oracle against the Render container and nothing more.
- **`SameSite=Lax` is doing real work.** It is what keeps §1 self-inflicted
  rather than CSRF-able, and it is why the `/api/*` POST surface does not need
  tokens.

**Lens (b) keeps sitting out** (10-28's reasoning, endorsed by 11-04, 11-11 and
11-18): five of fourteen runs have taken it and the answer is always "move off
flat JSON", which is a project, not a finding. Its role is as an *amplifier* —
§2 and §3 are this week's instances, and both land on the same single event
loop.
