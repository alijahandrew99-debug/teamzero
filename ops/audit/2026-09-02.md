## 1. Metered usage was computed from a stale snapshot and silently erased — FIXED

**`lib/plans.js:357` (`consumeVoiceMinutes`) and `lib/plans.js:387` (`consume`)** ·
confidence: **high, reproduced** · branch
`audit/2026-09-02-consume-stale-snapshot`

Both functions are read-modify-writes on a counter, and both took `before` from an
account object the **caller** supplied:

```js
// lib/plans.js:387 — before
function consume(account, n, owner = false) {
  const before = rolled ? 0 : Number(account.leadsUsed || 0);
  const used = before + n;
  db.updateAccount(account.id, { leadsUsed: used, usagePeriod: key });
}
```

`db.updateAccount` writes to disk but does not touch the caller's object. So if that
object was read before an `await`, `before` is already out of date, and writing
`before + n` **overwrites everything else that metered the account in the meantime.**

### Why this is routine, not theoretical

The night shift does it by design, every night, for every scheduled profile
(`server.js:681-684`):

```js
agents.keeperRun(p.accountId, p.id)      // not awaited — runs concurrently
  .then(...)
startProspectJob(p.accountId, p.id, { count, hints: s.hints || '', thenDraft: true, notify: true });
```

Both meter leads against the same account. `keeperRun` (`lib/agents.js:523-540`)
reads the account at the top of each iteration, then:

```js
const acct = db.getAccount(accountId);      // agents.js:524 — leadsUsed = N
...
const d = await outboundDraft(p, lead);     // agents.js:533 — seconds of AI time
...
plans.consume(acct, 1, false);              // agents.js:540 — writes N+1
```

During that `await`, the prospect job's `onProgress` (`server.js:227-231`) meters
every lead that lands. Then `keeperRun` resumes and writes `N + 1`, discarding all
of it. It repeats per iteration, so a 50-lead night-shift run drafting alongside
~10 follow-ups loses most of the run's metering.

### Reproduced

`node` against a throwaway `DATA_DIR`, simulating exactly that interleaving:

```
=== BEFORE FIX (origin/main) ===
FAIL  leads: 20 metered during a keeperRun await + 1 draft: got 1, want 21
FAIL  voice: 7 minutes billed during another call's window + 3: got 3, want 10
FAIL  topup: leadsUsed after 1 then 5: got 2004, want 2005
FAIL  topup: drawn only for the 5 past the limit: got 96, want 95
```

21 leads metered, **1** recorded. The voice case is the same shape: two calls whose
`/voice/status` handlers straddle one another bill 10 minutes and record 3.

The top-up rows matter as much as the counters: a stale snapshot also re-derives
`draw`, so the top-up balance a customer **paid for** drifts from what they actually
used (96 vs 95 above — in that direction by luck, not design).

### The fix

Both functions now re-read the account:

```js
const cur = db.getAccount(account.id) || account;
```

`lib/db.js` is entirely synchronous (`readFileSync`/`writeFileSync`), so the re-read
and the write below it cannot interleave — the whole update becomes atomic. This is
the pattern the codebase already applies in two other places for exactly this
reason: the per-iteration re-read at `lib/agents.js:473` ("*a snapshot taken once
before the loop meant leadsUsed only ever advanced by 1 per RUN*") and the
`sentToday` re-read at `server.js:557` ("*Re-read rather than trusting the
start-of-job snapshot*"). This run just extends it to the two functions that own the
counters.

The change errs toward counting usage that is currently lost, never toward billing
more than was used. Top-up drawdown is unchanged and still charges only what crossed
the plan limit.

**Verification:** `node --check` clean; the reproduction above goes all-green; the
repo's four suites (`test-reps`, `test-spam`, `test-voiceprofiles`, `test-assistant`
— 87 assertions) all pass. Also covered: owner accounts still never metered,
sequential consumption unchanged, and a synthetic account object not in the store
falls back to the passed object rather than throwing.

**One consequence worth stating plainly before you merge:** customers who have been
under-metered will now be metered correctly, so some accounts will appear to consume
their allowance faster than they did last month. That is the counter telling the
truth, not a new charge — but it is a visible behaviour change and it is yours to
time.

## 2. Two collections still use a GLOBAL retention cap, which the codebase already
## knows is wrong

**`lib/db.js:188` (`calls`, 3000) and `lib/db.js:361` (`smsThreads`, 2000)** ·
confidence: **high** · **reported, not fixed** — see the trap below

`lib/db.js:547` already says it, about the activity log:

> *Cap per ACCOUNT, not globally — a global cap meant one busy tenant silently
> deleted every other tenant's history.*

That fix exists and works (`capPerAccount`, `lib/db.js:549`). It was never carried
across to the two collections that still do a global `slice()`. So this is not a
judgment call about retention policy — it is a fix the author already made and
documented as necessary, applied to one of three collections.

`calls` is last week's finding 3a. **`smsThreads` is new, and it is the worse of the
two**, for two reasons.

**(a) It is live state, not history.** A call row is a record of something finished.
An SMS thread is an in-flight conversation — `server.js:1097` reads
`db.getThread(account.id, from)` to recover context when a text arrives, and the
missed-call text-back flow depends on it. Evicting one mid-conversation means the
next reply from a real customer arrives with no history behind it.

**(b) Eviction is by creation order, not recency.** `saveThread` updates in place:

```js
// lib/db.js:358-361
const i = all.findIndex((t) => t.accountId === accountId && t.phone === phone);
...
if (i === -1) all.push(row); else all[i] = row;
write(F.smsThreads, all.slice(-2000));
```

An updated row keeps its original index, so `slice(-2000)` keeps the last 2000 rows
**by creation**. A thread created this morning and texted on all day sits at a low
index and is evicted before a newer thread nobody has touched. `saveCall`
(`lib/db.js:186-188`) has the identical shape.

**Volume, honestly:** at today's customer count neither cap is being hit — this is a
"before you have 200 customers" item, same bracket as last week's 3a, not something
biting this week. I could not measure the real files (`data/` is gitignored and I
stayed on anonymous public GETs).

### The trap, if someone fixes this

`capPerAccount` walks **forward** and keeps the first N per account, because
`logActivity` `unshift`s and is newest-first (`lib/db.js:550-552`). `calls` and
`smsThreads` `push` and are **oldest**-first. Dropping `capPerAccount(all)` in
as-is would keep the OLDEST N per account and silently delete everything recent —
precisely the failure its own comment warns about. It needs a reverse (or a
`newestFirst` flag), and it needs a test that asserts which rows survive.

I did not ship this. It is a retention change on two collections, it has a
data-destroying failure mode if the ordering is got backwards, and the Keeper has
`keeper/2026-09-02-db-write-compact` in flight on `lib/db.js` today — two routines
editing the same file on the same day is how a bad merge happens. Worth doing
deliberately, with the ordering test, after that branch lands.

## What I checked and found sound

Stating these so future runs don't re-spend the effort.

- **The night-shift scheduler cannot double-fire.** `checkSchedules` runs every 60s
  and a run takes far longer than that, which looked like a way to stack overlapping
  runs on one profile. It is not: `lastRunDate` is stamped at `server.js:663`
  **before** the run is launched, and the guard at `server.js:650` skips anything
  already run today. Correctly ordered.
- **The two metering loops re-read per iteration.** `lib/agents.js:473` and `:524`
  both take a fresh account inside the loop. The "advances by 1 per run" bug the
  comment describes is genuinely fixed; finding 1 is the *cross-run* remainder of
  the same family, which that fix could not reach.
- **`sentToday` is defended.** `server.js:555-559` writes the count then immediately
  re-reads and takes the max, with a comment naming the exact hazard.
- **`spam.strike` is safe** (`lib/spam.js:94-106`) — `rec()` through
  `patchCollection` with no `await` anywhere, so the read-modify-write is atomic.
  Same for `hooks.ensureSecrets` (`lib/hooks.js:21-27`).
- **`db.write` is crash-safe for a single process** (`lib/db.js:44-48`): temp file
  then `renameSync`. A kill during `writeFileSync` leaves the target untouched; a
  kill between write and rename leaves it untouched. `ENOSPC` throws before the
  rename. I went looking for a torn-write path to `data/*.json` and did not find
  one.
- **`logActivity` is properly bounded per tenant** (`lib/db.js:563-567`), unlike the
  two collections in finding 2.
- **Append-shaped db helpers are atomic.** Every `read → push → write` in db.js
  completes in one synchronous call, so concurrent requests cannot interleave inside
  one. The concurrency hazard in this codebase is exclusively application code
  holding a value across an `await` — which is why finding 1 is the whole story
  rather than one of many.

### One thing I could not settle

`db.write` uses a **fixed** temp filename, `f + '.tmp'` (`lib/db.js:45`). With one
process that is fine and I confirmed it. With two processes sharing `DATA_DIR` it is
not: both write the same tmp path, one renames interleaved content over the real
file, `read()` then swallows the parse error and returns `[]` (`lib/db.js:43`), and
the next write persists that empty array — total, silent loss of a collection.

Whether two processes can ever overlap depends on Render's deploy behaviour for a
service with a persistent disk, which I can't determine from in here. render.yaml's
comment claims zero-downtime via `healthCheckPath`, which would imply an overlap
window; Render generally does *not* do zero-downtime for disk-backed services,
which would mean no window. **Worth one look at the Render dashboard** — if deploys
ever overlap, this is a one-line fix (unique tmp name) against a catastrophic
failure mode. I am flagging it rather than reporting it as a finding because I could
not establish the trigger, and a hypothetical dressed as a bug wastes your time.
