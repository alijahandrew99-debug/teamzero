# Dawnpipe code audit — 2026-08-26

**Lens this run: (d) the voice call state machine in `server.js` — stuck/orphaned
states and double-billing of voice minutes.**

First audit run, so there is no prior lens to rotate away from. Picked (d)
because voice is ~95% of cost of goods (COST.md) and plan minutes are the thing
customers actually pay for — a billing bug there is felt directly, in money, by
someone who is paying $499/mo.

All line numbers are against `origin/main` at `c924801`.

**No CRITICAL findings.** Nothing actively exploitable, no data-loss path in
flight, no double-billing of the same call.

## 1. Restart-recovered calls were billed even when nobody spoke — FIXED

**`server.js:1840-1848`** · confidence: **high** · branch pushed

`/voice/status` has two billing paths, and they disagree.

The live path (in-memory call still present) is careful:

```js
// server.js:1856-1861
const callerSpoke = (call.turns || []).some((t) => t.who === 'caller' && String(t.text || '').trim());
const acctForBill = db.getAccount(call.accountId);
if (acctForBill && callerSpoke && !call.spamCall) plans.consumeVoiceMinutes(acctForBill, Math.ceil(dur / 60), ...);
```

with the reasoning spelled out right above it: *"Robocalls, dead air and pocket
dials were eating paid minutes and could push a shop into message-only mode
mid-month."*

The fallback path — the one that runs when the in-memory record is gone —
billed unconditionally:

```js
// server.js:1840-1846
if (!call && sid) {
  const owner2 = db.accountByCallSid(sid);
  if (owner2) {
    const dur0 = Number(params.CallDuration || 0);
    db.saveCall(owner2.id, { sid, status: params.CallStatus || 'completed', durationSec: dur0 });
    plans.consumeVoiceMinutes(owner2, Math.ceil(dur0 / 60), stripe.isOwner(owner2));
  }
```

No `callerSpoke` check. No `spamCall` check.

**Failure scenario.** A robocall dials a customer's line. The AI answers, the
recording plays, and either the tripwire (`server.js:1456-1463`) or the model
(`1568-1577`) hangs up and flags it `spamCall` — "not billed", says the activity
log the owner reads. Meanwhile Render finishes auto-deploying `main`. The
process restarts, `voice.getCall(sid)` returns null, and when Twilio's status
callback lands it takes the fallback and charges the full rounded-up duration
against the plan. Same for a pocket dial or a caller who hung up on the greeting.

The trigger is timing, not input: whether a deploy landed while the call was up.
Render auto-deploys `main` and the Keeper pushes daily, so this is not rare —
it is a few calls a week silently billed against the exact rule the product
promises not to bill.

**Fix (branch `audit/2026-08-26-voice-status-fallback-billing`):** the fallback
now reads the persisted call row and applies the same rule. Both signals are
already on disk by the time the handler runs — `server.js:1566` writes the
transcript on every turn, and the spam paths stamp `outcome: 'spam'` /
`'screened-out'` (`1429`, `1460`, `1574`).

**The trade-off, stated plainly, because it is a revenue change and yours to
veto:** the persisted transcript is a proxy for "the caller spoke", and it lags
by one turn. A call that died before the *first* agent reply has a caller turn
in memory that was never written, so it now goes unbilled. That is at most one
minute, on a call that also had to span a restart. I took the under-bill over
the over-bill deliberately — charging a customer for a robocall is the failure
that gets a Front Desk account cancelled; missing one minute is not. If you
want it the other way, the branch is one condition to change.

`node --check server.js` passes; the guard logic was table-tested against
transcripts with an agent-only turn, a real caller turn, a spam outcome, a
whitespace-only caller turn, and a row with no transcript at all.

## 2. `/voice/status` billing is not idempotent

**`server.js:1836-1848`** · confidence: **medium** (mechanism certain, trigger
unproven) · **hardening, not an active bug — reported, not fixed**

Nothing records that a call has been billed. The live path bills, then
`voice.endCall(sid)` (`server.js:1934`) drops the in-memory record — so a
*second* delivery of `/voice/status` for the same `CallSid` finds no call, takes
the fallback, and bills the whole call again.

I could not establish that a second delivery actually happens today, and I want
to be straight about that rather than dress it up. Both status callbacks are
registered completed-only: the number-level one (`lib/numbers.js:70`, `91`) and
the outbound Call-resource one (`lib/voice.js:898`, no `StatusCallbackEvent`).
Webhook errors do not cause a retry either, because the voice error handler
returns TwiML with a 200 rather than a 500 (`server.js:3479-3495`) —
deliberately, and it is the right call.

So this is a latent edge, not something billing customers wrongly this week.
It matters because the guard is cheap and the ways in are all things someone
would do casually later: adding `StatusCallbackEvent` to get ringing/answered
events, a proxy that retries on timeout, or a `<Number statusCallback=...>` on
the transfer leg. Any of those turns a one-line config change into
double-charged minutes with no alarm.

**Suggested fix:** stamp `billedMin` on the call row when minutes are consumed,
and skip billing if it is already set. ~6 lines across both paths. I left it
alone because it adds a field to the persisted schema and touches the live
billing path on every call — bigger than this run's remit.

## 3. `calls.json` is globally capped at 3,000 rows and rewritten whole on every turn

**`lib/db.js:183-190` and `lib/db.js:44-48`** · confidence: **high** ·
**reported, not fixed — architecture decision**

```js
// lib/db.js:188
write(F.calls, all.slice(-3000));
```

The cap is across **all tenants**, not per account. Two separate consequences,
both on the voice path.

**(a) Silent history loss.** At 200 Front Desk customers averaging ~150 answered
calls a month, that is ~30,000 calls/month against a 3,000-row store — roughly
**three days of history**, after which a quiet customer's calls are evicted by a
busy customer's volume. The app's call list reads `db.getCalls()`
(`server.js:2209`, `2605`), so the owner just sees their history end. Recordings
go with it: `/voice/recording` resolves the owner via `db.accountByCallSid`
(`server.js:1745`), which reads the same file, so a recording URL arriving after
eviction is dropped.

**(b) Event-loop stalls on the live call path.** `write()` does
`JSON.stringify(d, null, 2)` — pretty-printed — then `writeFileSync`, and
`saveCall` reads the whole file first. Measured on this box with realistic rows
(14 turns, ~180 chars per agent turn):

| rows | file size | read+parse | stringify+write |
|---|---|---|---|
| 500 | 1.5 MB | 14 ms | 18 ms |
| 1,500 | 4.4 MB | 40 ms | 34 ms |
| 3,000 | 8.9 MB | 37 ms | 98 ms |

At the cap that is **~135 ms of fully blocked event loop per `saveCall`**, and
`server.js:1566` calls it on **every conversational turn of every call**.
`/voice/status` adds another `saveCall` plus two full-file reads
(`server.js:1885`, `1924`). Node is single-threaded, so this is not per-call
overhead — every concurrent call queues behind every other call's writes. At
~3.5 turns/min per call that is roughly 8% of the event loop at 10 concurrent
calls and about half of it at 60, on top of `think()`'s 9-second AI budget,
against Twilio's 15-second webhook abandon.

I could not measure production `calls.json` (`data/` is gitignored and I only
use anonymous public GETs), so the table is the shape of the problem at the cap,
not today's number. Worth checking the real file size before deciding urgency.

This is COST.md's *"will not carry 200 customers of concurrent voice webhooks;
that is a correctness problem before it is a cost one"* with numbers attached.
It also says the Postgres migration is the answer, and I agree — but two cheap
things buy time and are worth doing whichever way that decision goes: drop
`null, 2` from `write()` (~40% smaller files and less CPU, zero behaviour
change), and make call retention per-account rather than global.

## 4. The do-not-call branch on `/voice/incoming` is unreachable

**`server.js:1288-1290`** · confidence: **high** · **product decision, not fixed**

```js
// server.js:1288-1290
const inDnc = suppress.isPhoneSuppressed(account.id, params.From || '');
db.logActivity(account.id, { agent: 'VOICE', msg: 'Incoming call from ' + (params.From || 'unknown')
  + (inDnc.blocked ? ' (this number is on your do-not-call list — they called you, so we answered)' : '') });
```

`inDnc.blocked` can never be true here. The identical check at
`server.js:1159` already `<Reject>`ed the call and returned, ~130 lines earlier.
`isPhoneSuppressed` is a pure read, so the two calls always agree.

This is not just dead code — the two sites encode **opposite policies**, and the
unreachable one is the one with the reasoning written down. Line 1288 says: if
someone on your do-not-call list rings *you*, answer them, because a DNC list is
about not calling *them*. Line 1159 says: reject them unheard. Line 1159 wins
silently.

**Both are defensible and it is your call, which is why I did not touch it.**
The `<Reject>` at 1159 exists to protect against a caller who told us to stop —
that is right for a robocaller. But "on the owner's own block list" and "asked
us to stop calling them" land in the same suppression bucket, and a real
customer who once asked not to be *called* and now rings the shop with a burst
pipe gets hung up on. Worth splitting the two reasons if you want 1288's
behaviour back.

## 5. `estimateCost` omits the transferred `<Dial>` leg

**`lib/voice.js:145-152`** · confidence: **high** · low severity ·
**reported, not fixed**

```js
const line = direction === 'outbound' ? RATE_VOICE_MIN_OUT : RATE_VOICE_MIN_IN;
return Number((mins * line + ...).toFixed(3));
```

One line rate, once. But a transferred call has two legs: the inbound call, and
the outbound leg Twilio dials to the tech (`sayAndDial`, `lib/voice.js:306-309`,
reached from `server.js:1632`). Twilio bills both. The child leg costs
`RATE_VOICE_MIN_OUT` ($0.014/min) for the bridged portion and is invisible here,
so `estCost` — shown to the owner per call in `views/app.html:1577` and totalled
at `1551` — understates every transferred call.

Small: ~$0.04 on a 5-minute call with 3 minutes bridged, against an `estCost`
near $0.80, and COST.md rightly notes the line rate is only ~4% of a minute's
cost. Not worth a fix on its own. Worth folding in whenever `estimateCost` is
next touched, because COST.md leans on these numbers for the architecture
decision and a known-low input should be a known-*and-corrected* one.

## What I checked and found sound

Stating these because "no finding" is only useful if you know where I looked.

- **Call termination is genuinely well-guarded.** I went looking for a call that
  could run forever and did not find one. Elapsed-seconds hard stop
  (`server.js:1479`), exchange cap with a `+4` hard stop (`1495-1496`), silence
  capped at 3 (`1436`), screening capped at 2 (`1426`). The noise-replay path
  (`1412-1419`) skips the silence increment, which looked like a way to stall —
  but `call.replayAt = call.turns.length` and the replay pushes nothing to
  `turns`, so it fires at most once per turn count and the silence counter still
  reaches 3. Traced a fully noisy call end to end: it hangs up on the 4th turn.
- **`pendingThink` cannot get stuck.** It is nulled on both the consumption path
  (`1372`) and the fresh-turn path (`1388`), so the ack → `<Redirect>` leg
  cannot loop, and an abandoned think is wrapped
  `.then(v => ({v}), err => ({err}))` so it can never surface as an unhandled
  rejection.
- **Minute accounting has no lost-update race.** `consumeVoiceMinutes`
  (`lib/plans.js:357-371`) is read-modify-write, which is exactly the shape that
  loses updates under concurrency — but `lib/db.js` is entirely synchronous
  (`readFileSync`/`writeFileSync`) and there is no `await` between the
  `db.getAccount` at `server.js:1857` and the `db.updateAccount` inside it. Two
  calls ending in the same millisecond cannot interleave. Worth remembering as a
  constraint the Postgres migration has to preserve deliberately, because it is
  currently free and will not be.
- **Twilio signature verification is correct** (`lib/voice.js:156-163`):
  length check before `timingSafeEqual`, fails closed with no auth token, and
  the signed URL is rebuilt from proxy headers rather than `PUBLIC_URL`, so a
  domain move does not reject every call.
- **Voice webhooks never return 5xx** (`server.js:3479-3495`) — they answer 200
  with graceful-exit TwiML. This is what stops a bug becoming a Twilio retry
  storm, and is why finding 2 is latent rather than live.
- **The in-memory `calls` Map does not leak.** Pruning is only triggered on
  `startCall` and only above 500 entries (`lib/voice.js:320`), which looked
  thin, but `MAX_CALL_SECONDS` is 600 and the prune threshold is an hour, so
  entries are always eligible by the time pressure arrives. The orphaned
  `specTimer` after `endCall` fires into `launchSpeculation`, which returns
  immediately on a null call (`server.js:405-406`).
- **The screening path cannot hit an undefined profile.** `scrProfile`
  (`server.js:1219`) looked unguarded, but the `if (!profile) return` at
  `1180-1181` runs first and resolves identically.

## Suggested queue additions

For Alijah or the Keeper to fold into `ops/IMPROVEMENT-QUEUE.md` — I did not
edit that file.

1. **Review and merge `audit/2026-08-26-voice-status-fallback-billing`** (finding
   1). Small, but it changes billing, so read the trade-off note above before
   merging rather than after.
2. **Drop `null, 2` from `lib/db.js:46`** — ~40% smaller files and proportionally
   less CPU on every write, no behaviour change. Cheapest single win on the voice
   hot path and independent of the Postgres decision. Slots in alongside queue
   item 1 ("db.js write safety").
3. **Per-account retention for `calls.json`** instead of the global
   `slice(-3000)` (finding 3a). Stops one busy tenant evicting another's call
   history and recordings.
4. **Idempotency stamp on voice-minute billing** — `billedMin` on the call row,
   checked before consuming (finding 2). Do this *before* anyone adds
   `StatusCallbackEvent` or a `statusCallback` on the transfer leg.
5. **Split "owner blocked this number" from "this number asked us to stop
   calling them"** in the suppression store, then decide which one `/voice/incoming`
   should reject on (finding 4). Product decision, needs Alijah.
6. **Fold the transferred `<Dial>` leg into `estimateCost`** next time that
   function is touched (finding 5). Not worth a branch of its own.
7. **Measure production `calls.json` size** via `/api/admin/spend` or the Render
   shell before pricing the Postgres migration — it decides whether finding 3b is
   already biting or still theoretical.
