## 1. The public call-back form had one uncapped field — FIXED

**`server.js:999`** · severity **Critical** · confidence **high, reproduced
end to end through HTTP** · branch `audit/2026-11-04-cap-consent-text`

`/f/<slug>` is the hosted request form. It is public, unauthenticated, and its
URL is *meant* to be published — `/api/callbacks` hands the customer the link and
an embed snippet to put on their website. Every field it stores is length-capped:

```js
// server.js:991-993
const name  = String(f.name  || '').trim().slice(0, 80);
const phone = String(f.phone || '').trim().slice(0, 24);
const need  = String(f.need  || '').trim().slice(0, 400);
```

Except one:

```js
// server.js:999
const consentShown = String(f.consentText || '').trim() || callback.consentText(biz, phone);
```

`f.consentText` is a hidden field the form posts back (`views/callback-form.html:49`),
so it arrives from the client, and nothing bounds it but `MAX_BODY`
(`server.js:73`) — **2MB per request**.

### Why 2MB in one field matters here and not elsewhere

It lands in `callbacks.json`, and `lib/db.js:29-35` is explicit about what that
file is:

> `// Every callback request, with the consent the person gave. This file is the`
> `// evidence: ... unaltered, append-only, never pruned.`

`addCallback` (`lib/db.js:523-529`) matches the comment — it has no cap, where
`logActivity` has `capPerAccount` and `saveCall` has a 3,000-row ceiling. And
`write()` re-serialises the whole collection on every insert. So each POST pays
the cost of every byte every previous POST stored.

### Measured, against the real `lib/db.js`

```
 rows   file      addCallback   readCollection
    1    2.1 MB        26 ms            7 ms
    5   10.5 MB       246 ms           51 ms
   10   21.0 MB       324 ms           82 ms
   15   31.5 MB       276 ms           93 ms
   20   41.9 MB       933 ms          135 ms
   25   52.4 MB       561 ms          182 ms
```

Twenty-five requests. Node is single-threaded, so that `addCallback` column is
the whole process stopped — no voice webhook, no Stripe webhook, no page load,
for half a second to a second at a time. `runCallbackQueue` (`server.js:379`)
re-reads the entire file **every 60 seconds** for ever after, which is the
`readCollection` column.

A Twilio voice webhook that does not answer in time is dead air on a live call to
a real plumber's real customer. Blocking the loop for ~0.9s per insert, at will,
is the whole instance.

### And the disk

Render Starter runs a 1GB persistent disk (COST.md). At 2MB a request that is
~500 requests to fill it. A full disk is one of the two triggers the 09-30 report
identified for store-file corruption — that path is now *contained* (quarantine
instead of overwrite, merged), so this is a hard outage rather than data loss.
Worth being precise about: the 09-30 fix is the reason this is not worse.

### Reproduced

Against the running server, as an anonymous client:

```
form slug: /f/ibww47os
  PASS  name is capped at 80
  PASS  need is capped at 400
  PASS  POST accepted (200)
  PASS  1,000,000 client bytes stored verbatim as consent evidence
  PASS  callbacks.json grew by ~1MB from ONE unauthenticated POST
  PASS  25/25 POSTs accepted past a 20/hour throttle by varying X-Forwarded-For
  PASS  no call was placed (no Twilio config)
final callbacks.json: 1.01 MB for 27 rows
```

**The throttle is not a brake.** `rateLimited` is 20/hour per IP on this route,
but it keys on `x-forwarded-for` (`server.js:135`) with no trusted-proxy hop
count — the 10-14 finding, still unfixed. Varying that header gave 25/25
acceptances above. So the only thing standing between a stranger and an
unbounded write is a header the stranger sets.

### The fix

`.slice(0, 2000)` on the client value. The genuine wording is 591 characters,
778 with a 200-character business name, so 2000 keeps every real submission whole
and takes the field out of the write-amplification business. One line plus the
comment explaining why the number is what it is.

`test-callbackform.js` is new — **9 assertions, 2 failing on `main`**. It also
asserts the *existing* caps, so they cannot be dropped later, and asserts that a
real consent wording still stores whole and still satisfies `consentValid()` and
`callbackAllowed()`. All six existing suites green (103 assertions).

### The half of this I did NOT fix: the evidence is forgeable

Same line, different problem, and it needs a decision rather than a patch.
`lib/callback.js:24-25` states the design:

> `// Everything that makes (1) hold up -- the wording, the timestamp, the IP --`
> `// is stored with the record exactly as shown, and never edited afterwards.`

But "exactly as shown" is taken on the client's word. A crafted POST sets
`consentText` to anything, and `consentValid()` (`lib/callback.js:51-53`) only
checks the string is **non-empty**:

```
  PASS  forged consentText passes consentValid()
  PASS  forged consentText passes callbackAllowed()
  PASS  stored evidence does NOT match the wording the server showed
```

`db.updateCallback`'s write-once lock (which 10-28 correctly called sound)
protects the record *after* it is created; it cannot help with what was written
at creation. In a TCPA dispute the stored wording is the exhibit, and an exhibit
the opposing party could have authored is not evidence.

Two layered things make this worse, and both are the same shape — nothing checks
that the person filling the form owns the number they typed:

- Anyone can enter a third party's number into any customer's published form and
  Dawnpipe will place an AI call to it, with "consent" on file. Bounded to one
  call per number per account per day by `calledToday`, and the do-not-call list
  still applies — but the first call always goes.
- The honest framing of the current state is that the consent record proves a
  box was ticked by *someone*, not by the subscriber of that number.

**Not implemented deliberately.** The real fix is either (a) reconstruct the
wording server-side from values the server already holds and store only that, or
(b) sign the hidden field so a round-trip is verifiable, plus (c) an SMS
confirmation before the first AI call. (a) is nearly free but changes what is
stored for existing records; (c) is a product decision with a cost per message
and a conversion cost. That is a call for Alijah, not a drive-by commit, and it
is in the queue additions.

## 2. `/api/profile/autofill` is a read-SSRF, and the content comes back out — NOT fixed

**`server.js:2526-2531`, `lib/agents.js:97-117` and `:118-152`** · severity
**High** · confidence **high on the primitive, reproduced against a loopback
target; uncertain on what is actually reachable from Render**

The 10-14 report looked at SSRF and concluded `hooks.emit` was "real but thin"
because no response body ever returns to the caller — only a status code reaches
the activity log. That verdict is right, and the existing queue item ("IP-range
guard on outbound customer-supplied fetches") was written for that thin case.

This one is not thin. The content comes back.

```js
// lib/agents.js:104 — no address check, redirects followed
const r = await fetch(url, { signal: AbortSignal.timeout(ms), redirect: 'follow', ... });
```

```js
// lib/agents.js:121 — only a missing scheme is defaulted; an explicit http:// is kept
if (u && !/^https?:\/\//i.test(u)) u = 'https://' + u;
```

The fetched bytes go into the model prompt as `WEBSITE (${hostname}):\n${text}`
(`lib/agents.js:164`), and the prompt instructs the model to return
`faq: the facts the AI may state, from the site only` and
`pricing: prices ONLY if stated explicitly on the site, **copied exactly**`. The
drafted fields are returned to the caller as JSON (`server.js:2529`). So a
request to an internal address comes back to the attacker as a paraphrase of that
address's response, with anything price-shaped quoted verbatim.

### Reproduced

Against a loopback HTTP server started by the test, with `callAI` stubbed so
nothing left the box and no AI spend was incurred:

```
  PASS  http:// loopback URL is fetched (no address check)
  PASS  internal content is returned to the caller in the API response
  PASS  the URL is taken verbatim when a scheme is present (http not forced to https)
  PASS  a 302 to a loopback address is followed (redirect: follow)
  PASS  one call probes 4 paths, then 3 more on the www retry
         (4 requests to the target from a single /api/profile/autofill call)
```

The `redirect: 'follow'` line is what makes an allowlist-by-scheme useless:
`https://attacker.example/` returning a 302 to `http://10.0.0.5:8080/` is
followed, so even forcing https buys nothing.

### Who can reach it

A brand-new account with no card. `server.js:2457-2459` grants two free
autofills to a locked account specifically so the in-person demo works before
payment, and signup is throttled only by the per-IP limiter that §1 shows is
header-controlled. So: effectively unmetered, from anyone, with four requests per
call.

### What I can and cannot say about impact

What is **verified**: loopback and private-range addresses are reachable, any
port, http allowed, redirects followed, four requests per call, response content
returned in paraphrase.

What I did **not** verify, and will not: whether a cloud metadata endpoint or
another service on Dawnpipe's Render private network actually answers. Checking
that means probing production from the inside, which the brief forbids and which
I would not do on a live revenue service anyway. Render's private networking does
give services in an account internal hostnames, so "something is reachable" is
the way to bet, but I am not going to dress a bet as a finding.

### Why I did not patch it

This is not a null check. A correct fix is: resolve the hostname, reject
loopback / link-local / private / CGNAT / IPv6-mapped ranges, pin the connection
to the resolved address so DNS cannot be rebound between check and connect, and
re-run all of that on **every** redirect hop rather than handing `fetch` the
follow. In zero-dependency Node that is a custom redirect loop with a
`lookup` hook, and it has to not break the legitimate case this feature exists
for — small-business sites behind WAFs, the www retry, the four-page fan-out.
Getting it subtly wrong either breaks onboarding for real customers or leaves the
hole open while looking closed. It wants a design and a test matrix, not a
drive-by. Sketch is in the queue additions.

## 3. Signup accepted any string as an email — FIXED (and the context that made it matter)

**`server.js:2270`, `views/app.html:1845`, `views/app.html:1110`** · severity
**Medium** · confidence **high on every component, medium on the full chain** ·
branch `audit/2026-11-04-validate-signup-email`

```js
// server.js:2270
if (!email || pw.length < 6) return errSignup('Enter a valid email and a password of 6+ characters.', 400);
```

The message promises "a valid email". The test is "not empty". `/partners/apply`
(`server.js:2165`) applies a shape check to an address a stranger supplies;
signup, which creates the record the rest of the product trusts, applied none.

### Why an account's email is not inert

**First, confirmed in a real browser: `esc()` does not protect a JS string inside
an HTML attribute.** 10-28 raised this as a hypothesis for this run. It holds.
Replicating `views/app.html:1845` exactly, in Chromium:

```
attacker email        : "x';window.__pwned=1;//"
esc() output          : "x&#39;;window.__pwned=1;//"
onclick as the DOM has: "document.getElementById('as_email').value='x';window.__pwned=1;//';..."

  CONFIRMED: esc() did NOT protect the JS string in the onclick attribute
  OK: esc() DOES still protect the plain-text context
```

The browser HTML-decodes an attribute before parsing the JS in it, so `&#39;`
becomes a real quote and the string closes. `esc()` is correct for text and for
quoted attributes; this is the one context it cannot cover, and the 09-16
quote-escaping fix does not change that.

The address reaches that context via `/api/admin/reps/unattributed`
(`server.js:3262-3267`), which lists **other accounts'** emails to the owner.
Script running there runs as the only account that can reach `/api/admin/*` — rep
payouts, Stripe price creation, usage reconciliation, the Twilio spend ledger.

It also reaches `/app` unescaped: `page.replace('__EMAIL__', account.email)`
(`server.js:2422`) into `views/app.html:166`. That one is self-XSS and genuinely
Low.

### The gate, stated honestly

`reps/unattributed` filters on `subStatus` in `active`/`trialing`, and reaching
either means completing Stripe Checkout — card required, deliberately
(`lib/stripe.js:338-344`). `createCheckout` passes the account address as
`customer_email` (`lib/stripe.js:354`), so **Stripe's own email validation is
currently an unintended gate on this chain.** I did not test what Stripe accepts;
doing so means creating real Checkout sessions against the live key. A local part
may legitimately contain an apostrophe (`o'brien@example.com` is a valid
address), so I would not assume the gate holds — but I am not claiming it falls
either.

That dependency is itself the finding worth stating plainly: the thing presently
preventing a stored XSS against the highest-privilege account in the system is a
third party's input validation, and nothing in Dawnpipe's own code.

### The fix

The `/partners/apply` regex and its 120-character cap, applied at the point the
record is created. Creation only, so an account that predates the check can still
log in — asserted, because production may already hold such rows.

`test-signup.js` is new — **16 assertions, 8 failing on `main`**. Eight hostile
shapes refused; four ordinary addresses that must not become collateral damage
accepted (`name+tag@`, `o'brien@`, `first.last@example.co.uk`,
`user_name@sub.example.com`); and the legacy-login case.

**The `onclick` half is NOT fixed.** The real answer is the `data-*` attribute
plus delegated-listener refactor 10-28 already put in the queue, and it touches
many call sites across a 2,434-line file. Validating the input closes the only
externally-supplied path into that sink today; the sink itself stays on the
queue, and anything else that ever renders customer text through an inline
handler reopens it.

## 4. `/u/<token>` reflected a lead's address into HTML — FIXED

**`server.js:2086`** · severity **Low–Medium** · confidence **high** · branch
`audit/2026-11-04-escape-unsub-email`

```js
return done('You’re unsubscribed', `We’ve removed <b>${parsed.email}</b>. ...`);
```

**A correction to last week's nomination first.** 10-28 flagged this as forgeable
because `suppress.tokenFor`/`parseToken` fall back to `'dev-insecure-secret'`
when `SESSION_SECRET` is unset. I checked the infrastructure rather than the
code: `render.yaml:33-34` declares `SESSION_SECRET` with `generateValue: true`,
so a service created from the blueprint has a real generated secret and **the
forgery path 10-28 described is not live on dawnpipe.com** unless the variable
was removed in the dashboard. The "fail loudly when `SESSION_SECRET` is unset"
queue item is still right as defence in depth, but it should not be sold as
closing an open hole, and the 09-16 reflected-XSS framing of it was too strong.

What remains without the secret: the address inside a *legitimately minted* token
is a **lead's**, which arrives from a CSV import, a `/v1` push or a prospecting
run, and nothing checks its shape — `lib/smtp.js:104-107` refuses only a CR or
LF. So an account holder can get a valid `dawnpipe.com/u/...` URL that reflects
markup of their choosing, on an origin same-site with the app; `HttpOnly` stops
cookie theft but not same-origin requests to `/api/*` with a reader's session.
That chain has real gates (the send must succeed for the link to be observable),
which is why this is Low–Medium and not higher.

Either way, escaping one external value on an output path costs nothing and
depends on neither assumption. `test-unsubscribe.js` is new — **9 assertions, 4
failing on `main`** — and it asserts the opt-out still *happens* for a
hostile-looking address, because suppression failing would be a worse bug than
the one being fixed.

## Checked and clean

Recorded so a future run can skip them. Read, not sampled.

- **Both webhook signature verifications are correct.**
  `stripe.verifyWebhook` (`lib/stripe.js:476-485`) builds `t.body` over the raw
  body, compares with `timingSafeEqual` behind a length check, and parses only
  after verifying. `voice.verifySignature` (`lib/voice.js:156-163`) sorts params,
  HMAC-SHA1s against the auth token, length-checks then `timingSafeEqual`s, and
  **fails closed on a missing token**. Every `/voice/*` and `/sms/incoming` route
  is behind it (`server.js:1119`, `:1209`).
- **The Stripe webhook still has no timestamp tolerance**, so a captured event
  replays for ever. Already a queue item from 09-16, re-verified present. Worth
  noting the asymmetry: *our own* outbound webhook verifier does it properly —
  `hooks.verify` takes `toleranceSec = 300` and enforces it (`lib/hooks.js:60-62`).
  The fix for `verifyWebhook` is three lines modelled on code already in the repo.
- **All 12 `/api/admin/*` handlers are owner-gated** as their first statement —
  re-verified individually at `:3058, 3118, 3199, 3216, 3224, 3248, 3263, 3269,
  3275, 3281, 3289, 3336`, plus `/api/billing/diag`'s gate at `:3329`. `isOwner` fails closed
  on an unset `OWNER_EMAILS`.
- **No generic static-file route exists, so there is no path-traversal surface
  at all.** Checked mechanically rather than by eye: `view()` (`server.js:52`)
  and both `fs.readFileSync(path.join(VIEWS, …))` call sites (`:953`, `:1098`)
  are only ever reached with a string literal — the single non-literal argument
  in the file, `server.js:2149`, is a ternary over two literals. A real strength
  of the zero-dependency design, and worth not losing the next time a page is
  added.
- **`/f/<slug>` is sound apart from §1.** Slug regex `^\/f\/[a-z0-9]{4,24}$`,
  honeypot checked before validation, phone normalised to E.164 before storage,
  consent must be an affirmative `'1'`, IP and UA recorded, dial deferred so the
  page never waits on Twilio. `voice.esc()` is applied to every value
  interpolated into the rendered form, including the attribute contexts.
- **`/partners/apply` caps every field** (80/120/200/1000) and shape-checks the
  email. It is the pattern §1 and §3 were missing, in the same file.
- **`lib/smtp.js`'s `noLineBreaks` guard is still in place** on the envelope
  sender, the recipient, the attachment name/type and the unsubscribe URL
  (`:123-129`). The CRITICAL that led 09-16, 09-30 and 10-07 remains closed —
  checked in the code, not taken from the merge log.
- **`/api/settings/smtp/test` → `smtp.verify`** connects to a customer-supplied
  host and port. It is a TLS-only connect with a 20s deadline that returns only
  `{ok:false, error}`, and the customer is already trusted with their own mailbox
  credentials, so it is a weak port-scan oracle rather than a data path. Folding
  it into the same address check as §2 would be free; it does not earn its own
  work.
- **Password handling.** `scrypt` with a 16-byte random salt per account,
  `timingSafeEqual` on verify (`lib/auth.js:7-17`). Session cookies are
  `HttpOnly`, `SameSite=Lax`, `Secure` whenever `PUBLIC_URL` is https, HMAC-signed
  with a length check before `timingSafeEqual`.
- **`/forgot` reveals nothing** about whether an address is registered, and says
  so for a server-side reason (no system mailbox) rather than an account-side one.
- **No secret reaches a response or a log.** Re-grepped every `logActivity`,
  `console.*` and JSON response this run; 10-14's verdict holds.
- **`/v1/*` key comparison** uses `===` rather than a constant-time compare
  (`server.js:2331`). Over HTTP, against a 48-hex-character random key found by a
  linear array scan, a timing oracle is not a realistic attack. The *real* problem
  on that line — a full `allAccounts()` scan before any throttle — is 10-14's
  finding 3 with a branch already open (`keeper/2026-10-16-v1-unauth-rate-limit`).

9. **Length-cap the business profile `name` field** (`/api/profile/save`,
   `server.js:2540-2545`). Authenticated and self-inflicted, but it is
